[Codex CLI](https://developers.openai.com/codex/cli/) is OpenAI's terminal
coding agent. Bifrost connects it through a named custom provider backed by the
OpenAI-compatible Responses API.

<Tip>
Codex CLI sends a `session-id` header on every request, so a session sticks to
the provider and key that served it and keeps hitting the same prompt cache,
with nothing to configure. See [Session Affinity](/providers/session-affinity).
</Tip>

## Install Codex CLI

```bash
npm install -g @openai/codex
```

## Recommended: launch with Bifrost CLI

```bash
bifrost context add production \
  --base-url https://gateway.example.com \
  --use

# Enterprise user-scoped inference
bifrost auth login

# Or configure a virtual key
printf '%s\n' "$BIFROST_VIRTUAL_KEY" |
  bifrost auth set-virtual-key --stdin

# Confirm the virtual key allows this model before launching
bifrost models list

bifrost run codex --model openai/gpt-5
```

<Note>
A new virtual key with no `provider_configs` denies all providers by default.
Make sure `openai/gpt-5` (or the model you choose) appears in
`bifrost models list` before launching, or the request is rejected.
</Note>

Bifrost creates an isolated temporary `CODEX_HOME` for the launched process and
declares a `bifrost` model provider. It copies the user's `config.toml` first,
preserving MCP servers, project trust entries, reasoning preferences, and other
non-auth settings before replacing the model-provider routing. The user's
normal authentication and session history remain isolated, and changes Codex
makes inside the temporary home are discarded when the process exits.

Enterprise SSO and virtual keys are both supported. With SSO, Codex receives
the current Bifrost agent access token only in its child-process environment.
The token is not written to the temporary Codex provider configuration.

<Warning>
Codex currently receives one agent access token when the process starts. If a
long-running Codex session reaches token expiry, exit and relaunch it through
Bifrost so the CLI can refresh the Enterprise session first.
</Warning>

## Configure Codex manually with a virtual key

<Warning>
Codex prefers an existing OpenAI OAuth session over custom API credentials. Run
`/logout` before using a manually configured Bifrost provider. This is not
required for `bifrost run codex`, which uses an isolated temporary home.
</Warning>

Export the virtual key in the same terminal used to start Codex:

```bash
export OPENAI_API_KEY="your-bifrost-virtual-key"
```

Add a named provider to `~/.codex/config.toml`:

```toml
model = "openai/gpt-5"
model_provider = "bifrost"

[model_providers.bifrost]
name = "Bifrost"
base_url = "http://localhost:8080/openai/v1"
wire_api = "responses"
env_key = "OPENAI_API_KEY"
requires_openai_auth = false
supports_websockets = false
```

The trailing `/v1` is required because Codex appends `/responses` to the custom
provider URL. `supports_websockets = false` keeps the custom provider on
HTTP(S) Responses requests, which is required when Bifrost translates the
request to a provider that does not implement OpenAI's stateful Responses
WebSocket protocol.

<Warning>
Use a named `model_providers` entry. Setting only `OPENAI_BASE_URL` or
`OPENAI_API_KEY` can leave Codex on its built-in OpenAI provider, where OpenAI
OAuth and built-in transport behavior can take precedence.
</Warning>

## Sign in with ChatGPT through Bifrost

Teams on a ChatGPT workspace can keep Codex signed in with ChatGPT
and still send every model request through Bifrost. Codex keeps the ChatGPT
token in `Authorization`, and the Bifrost virtual key travels in `x-bf-vk`.
Bifrost checks the virtual key, drops it, and forwards the request to the
ChatGPT Codex backend with the ChatGPT headers unchanged. The ChatGPT seat pays
for the tokens. This follows OpenAI's
[Sign in with ChatGPT through a gateway](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway)
guide, using its header option. It works the same in the Codex CLI and in
Codex inside the ChatGPT desktop app, since both read the same Codex
configuration.

Add the provider to your workspace's cloud-managed `requirements.toml` in
ChatGPT's [managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration),
or to `~/.codex/config.toml` to try it on one machine:

```toml
model_provider = "bifrost"

[model_providers.bifrost]
name = "Bifrost"
base_url = "https://gateway.example.com/chatgpt_passthrough/backend-api/codex"
wire_api = "responses"
requires_openai_auth = true
supports_websockets = false
env_http_headers = { "x-bf-vk" = "BIFROST_VIRTUAL_KEY" }
```

Export the virtual key in the environment Codex starts from, then sign in with
ChatGPT inside Codex:

```bash
export BIFROST_VIRTUAL_KEY="sk-bf-..."
unset OPENAI_API_KEY
codex
```

Bifrost forwards two routes under this base URL, `GET /models` for the Codex
model picker and `POST /responses` for each turn. Bifrost refuses every other
path and method.

<Note>
Model names are the ones your ChatGPT plan offers, such as `gpt-5.5`, without
a provider prefix. Requests go straight to ChatGPT, so Bifrost routing,
fallbacks and non-OpenAI models do not apply on this path. Use the
[virtual key setup](#configure-codex-manually-with-a-virtual-key) for those.
</Note>

The virtual key's governance still applies. Bifrost checks each turn's model
against the key's allowed models, and budgets and rate limits count the usage
ChatGPT reports. The model list request names no model, so a key that allows
only some OpenAI models can still load the picker. Picking a model the key does
not allow fails on the first turn.

The ChatGPT token stands in for a Bifrost provider key, so no OpenAI key is
picked for these requests. Limits set on a provider key, key weights and the
key column in logs do not apply to them. Bifrost forwards only tokens that
ChatGPT issued. Any other `Authorization` value on this route, such as an
OpenAI API key or a token from your identity provider, never reaches ChatGPT,
and Bifrost sends its stored OpenAI key in its place.

<Warning>
Codex reads `BIFROST_VIRTUAL_KEY` once at launch and never refreshes it. After
you rotate the virtual key, restart Codex. The desktop app needs the variable
set on the app process itself.
</Warning>

### Sign in with your identity provider (Enterprise)

Bifrost Enterprise also supports the guide's native gateway OAuth option. Each
person signs in to your identity provider from Codex, so requests are
attributed to them and their user budgets, rate limits and access profile
apply. No virtual key is needed, and the token expires and refreshes like any
other sign-in.

Codex runs the whole sign-in against your identity provider. Bifrost takes no
part in it and only validates the token Codex sends afterwards, against the
SSO provider set up under **Governance → User Provisioning**.

1. In your identity provider, register a public client with PKCE and add the
   loopback redirect `http://127.0.0.1:43127/callback`. Use the port you set as
   `redirect_port` below. On Okta this is a native app. On Entra, add the
   redirect to the app registration Bifrost already uses for SSO, as described
   below. Codex cannot hold a client secret, so identity providers that require
   one on the token exchange, such as Google, do not work.
2. Point Codex at that client in `requirements.toml`, using your identity
   provider's authorize and token URLs:

```toml
model_provider = "bifrost"

[model_providers.bifrost]
name = "Bifrost"
base_url = "https://gateway.example.com/chatgpt_passthrough/backend-api/codex"
wire_api = "responses"
requires_openai_auth = true
supports_websockets = false

[model_providers.bifrost.gateway_oauth]
authorization_url = "https://your-org.okta.com/oauth2/default/v1/authorize"
token_url = "https://your-org.okta.com/oauth2/default/v1/token"
client_id = "your-codex-client-id"
scopes = ["openid", "email", "profile", "offline_access"]
delivery = { kind = "cookie", name = "auth-openid" }
redirect_port = 43127
```

The example uses an Okta custom authorization server. Include the scopes your
SSO login requests, and `offline_access` where your identity provider needs it
to issue refresh tokens, so Codex can refresh instead of sending people back to
the browser.

Codex sends the identity provider's access token, not the ID token, so it has
to pass the same checks as the SSO provider configured in Bifrost. The issuer
must match the SSO provider's issuer URL, and when the SSO provider sets an
audience, the token's `aud` must equal it. For an Okta custom authorization
server that audience is usually `api://default`.

<AccordionGroup>
<Accordion title="Microsoft Entra ID">

Entra issues the access token for whichever API the requested scopes belong
to. With only `openid`, `email` and `profile`, that API is Microsoft Graph, and
Bifrost rejects the token because its audience is Graph and its issuer is the
v1 `sts.windows.net` one. Codex has to request a scope that Bifrost's own app
registration defines.

In the [Microsoft Entra admin center](https://entra.microsoft.com), open
**App registrations** and select the app Bifrost uses for SSO.

1. Under **Expose an API**, set the **Application ID URI** to the default
   `api://<client-id>` if it is empty, then select **Add a scope**. Name it
   `access_as_user`, set **Who can consent** to **Admins and users**, and save.
2. Under **Manifest**, add the loopback redirect as a public client redirect
   URI and set the access token version to 2 inside the `api` object, so the
   token's issuer is `https://login.microsoftonline.com/<tenant-id>/v2.0` and
   its audience is the client ID. The portal's **Redirect URIs** field rejects
   `http` loopback addresses, so the manifest is the only place to add it.
   Entra ignores the port only for `localhost`, so the port must equal
   `redirect_port`:

   ```json
   "api": {
       "requestedAccessTokenVersion": 2,
   ```

   ```json
   "publicClient": {
       "redirectUris": ["http://127.0.0.1:43127/callback"]
   },
   ```

3. Under **Token configuration**, select **Add optional claim**, choose the
   **Access** token type and add `email`, so Bifrost can match the token to an
   existing user. Accept the Microsoft Graph permission prompt if one appears.
   Entra fills `email` only for users with a mail address.
4. Optionally, under **API permissions**, add the delegated `access_as_user`
   permission from **My APIs** and grant admin consent, so users don't see a
   consent prompt on first sign-in.

Then point Codex at Entra with the scope you created:

```toml
[model_providers.bifrost.gateway_oauth]
authorization_url = "https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/authorize"
token_url = "https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token"
client_id = "<client-id>"
scopes = ["openid", "email", "profile", "offline_access", "<client-id>/access_as_user"]
delivery = { kind = "cookie", name = "auth-openid" }
redirect_port = 43127
```

The scope names the API by its client ID rather than by `api://<client-id>`.
Codex signs in with the same app it requests the scope from, and Entra issues
a token an app requests for itself only when the API is named by its client
ID. Because Codex uses Bifrost's SSO app, the token's audience already matches
and Bifrost's Entra configuration needs no **Audience**.

</Accordion>
<Accordion title="Okta">

Create an **OIDC - OpenID Connect** app of type **Native Application** with the
**Authorization Code** and **Refresh Token** grant types, add the sign-in
redirect URI `http://127.0.0.1:43127/callback`, and assign it to the same users
and groups as your Bifrost SSO app. Okta matches redirect URIs exactly, so the
port must equal `redirect_port`.

Use the authorize and token URLs of a custom authorization server, such as
`default`: `https://<your-org>.okta.com/oauth2/<server-id>/v1/authorize` and
`/v1/token`. Its issuer must be the one set in Bifrost's Okta configuration,
and the token's audience must match the **Audience** set in Bifrost, if any.
The org authorization server (`/oauth2/v1/...`) does not work here, because
Okta issues its access tokens for Okta's own APIs and does not support
validating them elsewhere.

</Accordion>
</AccordionGroup>

Codex then sends two credentials on every request. The ChatGPT token stays in
`Authorization` and reaches ChatGPT unchanged; Bifrost forwards it only when
ChatGPT issued it. The identity provider token
travels in the `auth-openid` cookie. Bifrost validates it, attributes the
request to that user, and removes the cookie before forwarding. When
inference authentication is enforced, a missing or invalid cookie returns
`401`. The cookie name must be `auth-openid`.

<Note>
This option needs a Codex build with native gateway OAuth, a browser and a
reachable loopback port. It covers model requests only, not MCP, plugins or
voice.
</Note>

## Select a model

Pass the complete Bifrost model identifier when starting the session:

```bash
bifrost run codex --model openai/gpt-5
bifrost run codex --model anthropic/claude-opus-4-6
```

Or, when starting Codex directly from a manually configured shell:

```bash
codex --model openai/gpt-5
```

<Warning>
Codex's in-session `/model` picker uses Codex's model catalog, not Bifrost's
`/v1/models` response. Provider-qualified Bifrost models may not appear there,
and entering an arbitrary value after `/model` can leave the previous model
active. Use `/status` to verify the model. For a model outside the picker, exit
and relaunch with `bifrost run codex --model provider/model`.
</Warning>

The Bifrost launcher currently validates gateway connectivity and discovers the
permitted models, but it does not generate a Codex model-catalog file.

## Non-OpenAI models

Bifrost can translate Codex's Responses API requests to other configured
providers. The target model must support the tool calls Codex needs for file
operations, shell commands, and edits. Provider support for streaming,
reasoning items, parallel tools, images, and compaction can also differ.

<Note>
The current automated Codex cloud harness exercises the OpenAI provider path.
Treat other provider/model combinations as compatibility targets to validate
with your selected model before production rollout.
</Note>

A quick isolation sequence is:

```bash
bifrost models list --search claude-opus
bifrost chat --model anthropic/claude-opus-4-6 --message "Reply with OK"
bifrost run codex --model anthropic/claude-opus-4-6
```

Inside Codex, run `/status` before sending the first task. If Bifrost's error
payload reports a different `original_model_requested`, Codex did not switch to
the intended model.

## Troubleshooting

### The request still uses `gpt-5`

The in-session model change did not take effect. Relaunch with the desired
model on the command line and verify it with `/status`.

### The request is routed to the wrong provider key

Bifrost routes from the model actually sent by Codex. Inspect
`original_model_requested` in the error response or the Bifrost logs. Fixing a
provider-key error will not change Codex's active model.

### `401 Unauthorized`

When using Bifrost CLI, run:

```bash
bifrost auth status --output json
bifrost models list
```

When configuring Codex manually, confirm that `model_provider = "bifrost"`,
`requires_openai_auth = false`, and `OPENAI_API_KEY` contains a Bifrost virtual
key.
