Start with the conversation, then narrow down to the task and operation that needs attention. **Observability → Agent Logs** shows the traffic Bifrost handled for your registered agents.

## Find the request

1. Choose a time window that includes the request.
2. Filter by agent, status, task state, or caller. Enterprise deployments also expose the available user, project, team, customer, and business-unit filters according to your access.
3. Open an operation to inspect its details, or use session grouping to follow the conversation.

Search matches log metadata such as agent, operation, IDs, and errors. It does not search the contents of every message or artifact.

For these screenshots, we sent two questions to our research agent in one conversation and ran a separate travel-agent example. Your logs will contain your own agents, messages, and IDs.

## Follow a session

Session grouping uses the A2A context ID. A session can contain several tasks and operations, including follow-up messages, task reads, cancellation, and subscriptions.

Open the **Agent session** to see:

- **Operations** for the conversation, with stream events beneath their operation.
- **LLM Logs** for model calls whose session ID matches the context ID.
- **MCP Logs** for tool calls with that same session ID.

Use each list's pagination controls to continue through longer sessions. Changing the selected tab does not mean all of the conversation's logs have loaded at once. Operations without a context ID, such as initial card discovery, stay as individual rows.

<Accordion title="How grouping and filters interact">
The Group toggle groups matching request operations by context before paginating the session rows. A filter still applies inside those groups, so the displayed operation count can describe only the matching portion of a conversation. Stream events do not increase that operation count.

</Accordion>

To connect model and tool calls, your agent must [send the correlation headers](./integrating-your-agent). The gateway cannot infer those IDs from a separate model request.

## Open an operation

The detail view shows the operation, gateway status, agent, transports, available IDs, task state, and timing. The available tabs depend on the operation and data it produced.

We opened our research agent's `SendMessage` operation. The summary shows its status, IDs, transports, and latency; **Conversation** shows the request, completed task, and returned artifact.

| View | What to look for |
| --- | --- |
| Conversation | The message, returned task, status text, and artifacts. |
| Payload | Typed request or response details for non-conversation operations. |
| Events | Status and artifact updates associated with a stream or operation. |
| LLM Logs | Calls carrying this task ID as their agent correlation ID. |
| MCP Logs | Tool calls carrying this task ID as their agent correlation ID. |
| Raw Capture | Stored HTTP request and response bytes, when capture was enabled. |

An ID may be absent because the operation never had it. A card fetch has no task; an authentication failure may happen before the agent creates a context.

Agent operation timing measures the agent-facing work. Tokens and model cost belong to the correlated LLM logs; they are not separate token charges on the A2A operation itself.

### Inspect streaming work

Open a `SendStreamingMessage` or `SubscribeToTask` operation, then its **Events** tab. Events preserve their order and expose the available task, context, message, and artifact IDs.

Read task-state updates to follow progress. Read artifact updates to see output as it arrives. The final task state tells you whether work completed, failed, or needs input. A stream ending does not by itself mean the task completed.

We opened our travel agent's `SendStreamingMessage` operation and selected **Events**. Its five updates show the initial task, progress, artifact output, and completion in order. The first **Artifact updated** event is expanded to show the itinerary text emitted during the stream.

### Follow model and tool failures

For example, a research task fails while looking up documentation:

1. Open the failed task's agent operation and read its status message.
2. Open **MCP Logs** and inspect the matching tool call's input, output, and error.
3. Open **LLM Logs** to see whether the model requested the wrong tool or received an unusable result.
4. Return to the session to check whether a later message retried or continued the work.

A successful A2A response can contain a failed task. The operation's **Success** status describes the protocol response; read the returned task state in the conversation to see whether the agent's work succeeded. Where a row records a task state, the **Task state** filter helps narrow the results; a SendMessage request row may not record its returned task state in that filter field.

## Filter model and tool logs by agent

In **LLM Logs** or **MCP Logs**, use **Agents** to find calls associated with a registered agent's conversations. This matches each call's session ID against context IDs recorded in Agent Logs for that agent and time window.

Use **Session ID** to follow one conversation, or **Agent correlation ID** to narrow to one A2A task. Enter the task ID itself for that correlation filter.

<Note>
The Agents filter is conversation-based. If several agents share the same context ID, it can include their calls from that conversation. Calls without `x-bf-session-id` cannot join this filter, even if they have a task correlation header. The selected time window must include the corresponding Agent Logs too.
</Note>

## Export to observability connectors

Agent Gateway operations use the same observability connectors configured for LLM and MCP traffic. Configure the destination once, then use its A2A fields or metrics to find agent operations.

Exports cover `GetAgentCard`, `GetExtendedAgentCard`, `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask`, `CreateTaskPushNotificationConfig`, `GetTaskPushNotificationConfig`, `ListTaskPushNotificationConfigs`, `DeleteTaskPushNotificationConfig`, `push_notification`, and `push_delivery`. Each push-delivery retry is a separate operation, so failed attempts remain visible even when a later attempt succeeds.

| Connector | Agent Gateway representation |
| --- | --- |
| [OpenTelemetry](/features/observability/otel#agent-gateway) | Operation spans, stream events, structured content, optional raw HTTP bodies, and operation-duration metrics. |
| [Prometheus](/features/observability/prometheus#agent-gateway) | Duration histogram with operation counts, errors, and latency distributions. No message bodies. |
| [Maxim](/features/observability/maxim#agent-gateway) | Traces and operation spans with input/output, tags, errors, and streaming events. |
| [Datadog](/features/observability/datadog#agent-gateway) | APM spans, LLM Observability agent spans, and operation-duration metrics. |
| [BigQuery](/features/observability/bigquery#agent-gateway) | Rows with agent/task fields, structured input/output, and optional raw HTTP bodies. |
| [Pub/Sub](/features/observability/pubsub#agent-gateway) | JSON traces with operation spans, structured content, and stream events. |
| [Kafka](/features/observability/kafka#agent-gateway) | JSON traces with operation spans, structured content, and stream events. |
| [Splunk](/features/observability/splunk#agent-gateway) | Flattened operation events with input/output and operation-duration metrics. |

### Content and correlation

Structured content includes request messages, returned tasks and artifacts, and accumulated streaming output when available. Content suppression on a virtual key applies to exports, and connectors with a `disable_content_logging` setting can suppress bodies for that destination. Metadata and metrics remain available. The global log-store content setting and raw-capture setting do not replace connector content controls.

Raw HTTP capture is separate from structured content. OTel and BigQuery require their existing `export_raw_payloads` opt-in in addition to Agent Gateway capture. Maxim, Datadog, Kafka, Pub/Sub, and Splunk do not export those raw carriers. Prometheus exports no bodies. gRPC operations have structured content but no raw HTTP capture.

Incoming `traceparent` and `x-bf-session-id` headers provide distributed trace and session correlation for HTTP and gRPC requests. The A2A context ID remains a separate conversation identifier. To link the agent's subsequent LLM and MCP calls in Bifrost, continue to [send the correlation headers](./integrating-your-agent) described above. Task and session IDs stay in traces or logs rather than operation-duration metric labels.

## Inspect raw capture

Raw capture is disabled by default. Enable it in **Agents → Agent Settings → Capture Raw Request and Response**, then make a fresh request. The [configuration guide](./configuration#capture-raw-http-payloads) covers config.json and Helm deployment options.

Raw capture is separate from the structured conversation and event views. You can still read those views without storing raw HTTP payloads, subject to content-logging settings.

When capture exists, use the display and download actions to inspect the stored transport payload. A streaming HTTP response can contain SSE framing rather than one JSON document. gRPC raw capture is unavailable; use its structured details instead.

Capture is limited to 1 MiB in each direction. Oversized or incomplete bodies are omitted. A missing capture therefore does not mean the agent returned an empty response. Local push-config GET and LIST operations do not have an upstream HTTP exchange to capture.

<Note>
Raw transport bytes can include sensitive content and are not guaranteed to be secret-redacted. Parsed history redacts credential fields. Enable raw capture only where your logging policy permits it.
</Note>

## Understand timing

**Duration** is the operation's measured elapsed time. **Upstream latency** measures the agent-facing call. **Overhead** accounts for the remaining gateway work. Expand the overhead breakdown to see where that time went.

| Category | What it includes |
| --- | --- |
| Protocol library | A2A SDK request handling and protocol work. |
| Middleware | Authentication and request middleware. |
| Plugins | Governance, logging, and other enabled hooks. |
| Serialization | Parsing and encoding protocol payloads. |
| Processing | Gateway preparation and push configuration or delivery storage work. |
| Client delivery | Writing streamed output and waiting for a slow client. |

Protocol library time may account for a large share of a small operation's overhead. It is measured SDK handling time, not an LLM generation measurement. Push operations can have more processing time because they read or write durable configuration and delivery state. A local push-config lookup can therefore have overhead and no upstream latency.

Compare similar operations and transports. A long-lived stream and a single task lookup measure different work; their durations are not interchangeable benchmarks.

<Accordion title="Why are correlated logs missing?">
Check that the agent sends both headers on its outgoing Bifrost requests:

```http
x-bf-session-id: <A2A context ID>
x-bf-agent-correlation-id: <A2A task ID>
```

Task-level tabs match the task correlation ID. Session-level tabs match the context ID. Check the chosen time window, allow asynchronous log ingestion to settle, and confirm your account can read the related LLM or MCP logs. Calls sent directly to a provider or MCP server do not appear as Bifrost calls.
</Accordion>
