## What is Bifrost CLI?

Bifrost CLI is both:

- an interactive launcher for Claude Code, Codex CLI, Gemini CLI, and OpenCode; and
- a scriptable client for Bifrost inference, user-scoped usage, and management APIs.

Running `bifrost` without a command opens the launcher. Commands such as
`bifrost models list`, `bifrost usage`, and `bifrost providers list` can be used
directly from a shell or CI job.

The CLI stores gateway URLs and model selections as non-secret local state.
Virtual keys, management keys, and Enterprise session credentials are kept in
the operating-system keyring.

## Installation

```bash
npx -y @maximhq/bifrost-cli
```

The npm package is a small installer and launcher. It downloads the
platform-specific Bifrost CLI binary from Bifrost's release storage, verifies
its SHA-256 checksum when one is available, and then runs it. Node.js 18 or
later is required for this installation method.

Install or run a specific CLI release with:

```bash
npx -y @maximhq/bifrost-cli --cli-version v1.0.0
```

## Configure a gateway context

A context keeps one gateway URL, default model, selections, and an independent
set of keyring credentials. This prevents credentials from one environment from
being sent to another.

```bash
bifrost context add production \
  --base-url https://gateway.example.com \
  --use

bifrost context list
bifrost context show
```

Use `--context NAME` on any command to override the current context:

```bash
bifrost --context production models list
```

Persistent credentials and browser sessions always belong to a named context.
An ad-hoc `--base-url` can be used with credential environment variables, but
`auth login` and `auth set-*` refuse to store secrets until a context has been
created. Commands load only the credential types they need, so local config and
help operations do not depend on an available operating-system keyring.

<Note>
The CLI requires HTTPS for non-loopback gateway URLs before constructing a
request or starting browser authentication. Plain HTTP remains available for
local development through `localhost`, `127.0.0.1`, and `::1`.
</Note>

## Choose an authentication method

Inference and management APIs intentionally use different credentials.

### Enterprise browser SSO

```bash
bifrost auth login
bifrost auth whoami --output json
bifrost auth status --output json
```

The browser reuses the gateway's configured identity-provider session. The CLI
receives opaque Bifrost `ck-bf-agent-*` access and refresh tokens; it does not
read or store the browser cookie, IdP token, or password.

Enterprise SSO authorizes user-scoped inference, assigned virtual-key discovery,
budgets, rate limits, and usage. The gateway resolves the signed-in user and the
applicable access profile or assigned virtual key without returning a
virtual-key secret to the CLI.

```bash
bifrost virtual-keys assigned
bifrost usage
bifrost usage budgets --output json
bifrost auth select-virtual-key "$VIRTUAL_KEY_ID"
```

If the browser cannot be opened automatically, keep the CLI running and open
the printed URL on the same machine:

```bash
bifrost auth login --no-browser
```

The callback uses an ephemeral `127.0.0.1` port. Browser sign-in therefore does
not currently support completing the flow on a different workstation.

You can also sign in or out without leaving the interactive workflow. Run
`bifrost`, select the **Enterprise SSO** row, and press Enter. The launcher
temporarily leaves the full-screen view while it opens and prints the browser
URL, then returns to the same gateway context after authentication. Changing a
context's base URL clears its existing SSO session before saving the new URL.

### Virtual key

Use a virtual key for OSS inference, CI, or a harness that cannot carry the
Enterprise agent token:

```bash
printf '%s\n' "$BIFROST_VIRTUAL_KEY" |
  bifrost auth set-virtual-key --stdin
```

When both an Enterprise SSO session and a virtual key are stored, the CLI sends
only one automatic inference credential. Supported clients use the SSO agent
token; the virtual key is used when there is no signed-in session or the
harness cannot consume an agent token, such as Gemini CLI. Gateway credential
conflict policies apply only to a manually constructed request that explicitly
carries both credentials.

### Management API key

Browser SSO does **not** grant administrative management access. Provider,
credential, user, RBAC, and other administrative commands require a scoped
`bfst-*` management API key:

```bash
printf '%s\n' "$BIFROST_MANAGEMENT_KEY" |
  bifrost auth set-management-key --stdin

bifrost providers list
bifrost users list                       # Enterprise
```

For an OSS gateway protected by dashboard username/password authentication,
use:

```bash
printf '%s\n' "$BIFROST_ADMIN_PASSWORD" |
  bifrost auth login --username admin --password-stdin
```

## Launch a coding agent

Open the interactive launcher:

```bash
bifrost
```

Or launch a harness directly:

```bash
bifrost run claude --model anthropic/claude-sonnet-4-6
bifrost run codex --model openai/gpt-5
bifrost run opencode --model openai/gpt-5
bifrost run gemini --model gemini/gemini-2.5-pro
```

Direct aliases forward remaining arguments to the child CLI:

```bash
bifrost claude --resume
bifrost codex exec "summarize this repository" --json
```

### Harness authentication matrix

| Harness | Gateway path | Enterprise SSO agent token | Virtual key | Session refresh |
| --- | --- | --- | --- | --- |
| Claude Code | `/anthropic` | Yes | Yes | Automatic through a temporary token helper |
| Codex CLI | `/openai/v1` | Yes | Yes | Restart Codex after a token expires |
| OpenCode | `/openai` | Yes | Yes | Restart OpenCode after a token expires |
| Gemini CLI | `/genai` | Not currently | Yes | Virtual-key session |

<Warning>
Gemini CLI does not currently work with Enterprise browser SSO alone. Gemini's
API-key mode sends its credential as `x-goog-api-key`, while Bifrost agent
sessions authenticate with `Authorization: Bearer`. Configure a Bifrost virtual
key before launching Gemini when inference authentication is enabled.
</Warning>

Claude Code receives a temporary `apiKeyHelper` that asks Bifrost CLI for the
current agent token. The settings file contains no token and is removed after
Claude exits. Codex receives the current token in its child environment.
OpenCode receives it in an owner-readable temporary provider configuration,
which is removed when OpenCode exits. Persistent `bifrost configure` remains
virtual-key-only so short-lived user credentials are not written to long-lived
harness configuration.

## Model selection caveats

The launcher fetches `/v1/models` using the effective inference identity, so
the list reflects the selected user's or virtual key's model permissions.

### Codex CLI

Start Codex with the full Bifrost model identifier:

```bash
bifrost run codex --model anthropic/claude-opus-4-6
```

Codex's in-session `/model` picker is built from Codex's own model catalog. It
does not automatically contain the Bifrost `/v1/models` catalog, and typing an
arbitrary Bifrost model after `/model` may leave the previous model active. Use
`/status` inside Codex to confirm the model. Until Bifrost supplies a generated
Codex catalog, relaunch with `--model` when selecting a provider-qualified
Bifrost model.

Codex uses the Responses API. A non-OpenAI target must support the tool calls
required for file access, shell commands, and edits, and its Bifrost provider
adapter must support the corresponding Responses conversion.

### OpenCode

Bifrost generates a temporary OpenCode provider containing the model selected
at launch. OpenCode displays that generated provider as `bifrost/<model>`.
Relaunch from Bifrost to select a different gateway model that is not present in
the generated OpenCode provider.

### Claude Code and Gemini CLI

The model must support the tools and wire features the harness uses. Selecting
a model in Bifrost does not add missing upstream capabilities such as tool use,
vision, web search, or provider-specific reasoning controls.

## OpenCode appearance

The conversation area, prompt boxes, activity output, and model footer are
rendered by OpenCode. Bifrost gives the selected harness native terminal
passthrough, so launching it from the chooser has the same terminal rendering
behavior as running `bifrost opencode` directly.

Bifrost currently sets OpenCode's `system` theme when
`~/.config/opencode/tui.json` does not contain an explicit theme. Depending on
the terminal palette, this can produce a different appearance or lower contrast
than running `opencode` without Bifrost's temporary configuration.

To make the appearance deterministic, set an explicit OpenCode theme:

```json
{
  "$schema": "https://opencode.ai/tui.json",
  "theme": "opencode"
}
```

Save this as `~/.config/opencode/tui.json` and restart Bifrost CLI. Other
OpenCode themes, including `tokyonight`, `catppuccin`, and `system`, work the
same way.

## Native harness sessions

After you select a harness, Bifrost temporarily hands the terminal to that
process. Native passthrough preserves the harness's colors, cursor behavior,
keyboard handling, scrolling, and resize behavior. When the harness exits,
Bifrost restores the terminal and returns to the launcher chooser.

The previous multiplexer remains available as an opt-in when running several
harnesses in one terminal is more important than native rendering:

```bash
bifrost launch --tabs
```

Tabbed mode reserves the bottom terminal row for Bifrost and interprets the
harness output through a virtual terminal, so colors and cursor behavior can
differ from native mode.

## Gateway and management commands

```bash
bifrost status --output json
bifrost doctor
bifrost models list
bifrost usage
bifrost providers list
bifrost credentials list openai
bifrost virtual-keys list
bifrost teams list
bifrost resources list
```

The default `table` output is optimized for terminal reading. Collection
responses fit populated fields to the terminal width, show no more than eight
columns, prioritize identity and status fields, and summarize nested values
such as roles. When an API returns more fields, the CLI prints a notice below
the table. Use `--output json` or `--output yaml` whenever you need the complete
response for inspection or automation.

Use the generated OpenAPI operation catalog for endpoints without a first-class
wrapper:

```bash
bifrost api list --search virtual
bifrost api describe getVirtualKey
bifrost api call getVirtualKey --param vk_id="$VIRTUAL_KEY_ID"
```

Use `request` for a runtime route that is not in the bundled catalog:

```bash
bifrost request GET /api/version --auth none
bifrost request POST /v1/responses --auth inference --file request.json --stream
```

For buffered requests, `--timeout` limits the complete exchange. For streaming
requests, it limits only receipt of the response headers; once streaming has
started, the request context or user cancellation controls its lifetime. This
prevents a healthy long generation from being terminated by the default `30s`
timeout.

First-class management mutation commands and `bifrost api call` support
`--dry-run`; destructive operations additionally require `--yes`. The generic
`bifrost request` command is a low-level escape hatch and does not add these
safeguards.

The CLI uses stable process exit codes: `0` for success, `1` for general or
usage errors, `3` for authentication/authorization failures, `4` for not found,
`5` for conflicts, and `6` for timeouts or gateway/server failures.

## Local files and environment overrides

The CLI stores context metadata and per-context selections in
`~/.bifrost/state.json`. Legacy launcher defaults can still be read from
`~/.bifrost/config.json`. Secret values are excluded from both files.

Environment variables override keyring credentials for CI and temporary use:

- `BIFROST_BASE_URL`
- `BIFROST_CONTEXT`
- `BIFROST_VIRTUAL_KEY`
- `BIFROST_MANAGEMENT_KEY`
- `BIFROST_SESSION_TOKEN`
- `BIFROST_AGENT_TOKEN`
- `BIFROST_AGENT_REFRESH_TOKEN`
- `BIFROST_AGENT_VIRTUAL_KEY_ID`
- `BIFROST_OUTPUT`

## Troubleshooting

### `401 Unauthorized` after SSO login

Run:

```bash
bifrost auth status --output json
bifrost models list
```

Confirm that `inference_credential_type` is `enterprise-sso`. An SSO session
does not authorize administrative endpoints; configure a management API key for
those commands.

### Gemini asks for an API key

Configure a Bifrost virtual key with `bifrost auth set-virtual-key --stdin`.
Google account OAuth, Vertex credentials, and a Bifrost Enterprise agent token
are different credential types and are not interchangeable in Gemini CLI's
API-key flow.

### Codex still requests `gpt-5`

The in-session `/model` command did not select the provider-qualified model.
Exit and relaunch:

```bash
bifrost run codex --model provider/model
```

Then use `/status` inside Codex to verify the active model.

### OpenCode colors differ from a direct launch

Set an explicit theme in `~/.config/opencode/tui.json`. The `system` theme uses
the terminal's ANSI palette and can differ from OpenCode's default appearance.
Tabbed mode can introduce additional rendering differences.

### Models do not load

Check that the gateway is reachable, at least one provider is configured, and
the effective SSO identity or virtual key has permission to list the desired
models. Under the default `version: 2` semantics, an empty provider-key model
allow-list or virtual-key `allowed_models` list denies all models in that
scope; use `["*"]` to allow all models. `version: 1` retains the legacy
empty-means-allow-all behavior:

```bash
bifrost doctor
bifrost auth status
bifrost models list --output json
```
