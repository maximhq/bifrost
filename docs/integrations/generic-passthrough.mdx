## Overview

A **generic passthrough provider** is a custom provider whose `base_provider_type` is `generic`. It is a raw HTTP relay: Bifrost forwards the request bytes untouched to the API you configured and returns the upstream status and body unchanged, with the upstream headers except hop-by-hop headers, `Set-Cookie`, `Proxy-Authenticate`, `WWW-Authenticate` and the headers the gateway sets itself. Nothing about the request has to look like an LLM call.

What Bifrost still does on every call:

- Selects a key from the provider's key pool and injects it the way the API expects (bearer, custom header, query parameter, HTTP basic, or AWS Signature V4). Caller credentials are stripped.
- Pins the upstream host to the provider's `network_config.base_url`.
- On every call it dispatches, runs the plugin pipeline, writes a log row with the raw request and response bodies, and reports usage so governance counts the request against rate limits and charges budgets.
- Optionally confines the provider to the operations you listed (`strict_routes`), a list you can import from the API's OpenAPI document in the UI.

Each API is its own provider. The first segment after `/passthrough/` selects it:

```
POST /passthrough/tavily/search                  → https://api.tavily.com/search
POST /passthrough/textract/                      → https://textract.us-east-1.amazonaws.com/   (SigV4)
POST /passthrough/azure-tts/cognitiveservices/v1 → https://eastus.tts.speech.microsoft.com/cognitiveservices/v1
```

<Warning>
**Authenticate to Bifrost with your Bifrost virtual key, not the upstream API key.** Caller `authorization`, `x-api-key` and similar headers never reach the upstream; Bifrost always injects the key it selects from the provider's configured keys.
</Warning>

<Tab title="Web UI">

Key names are unique across all providers, so give each provider's key its own name; two keys named alike collapse into one stored key on config sync.

`network_config.base_url` is required. `allowed_requests` defaults to `passthrough` and `passthrough_stream`; no typed operation can be enabled on a generic provider, and `request_path_overrides` does not apply.

## `generic_config` reference

### `auth`

| Field | Applies to | Description |
| --- | --- | --- |
| `type` | all | `bearer` (default), `header`, `query`, `basic`, `aws_sigv4`, `none` |
| `header_name` | `header` | Header that carries the key, e.g. `x-api-key` or `Ocp-Apim-Subscription-Key` |
| `value_prefix` | `header` | Literal prefix placed before the key value, e.g. `Token ` |
| `query_param` | `query` | Query parameter that carries the key, e.g. `api_key` |
| `aws.service` | `aws_sigv4` | SigV4 signing name, e.g. `textract`, `translate`, `execute-api` |

- `bearer` sends `Authorization: Bearer <key>`; `basic` sends `Authorization: Basic base64(<key>)` where the key value is `user:password`.
- `aws_sigv4` signs the request with the key's `bedrock_key_config` credentials (static keys, an assumed role, or the default AWS credential chain when the key holds none). Caller signature headers (`x-amz-date`, `x-amz-security-token`, `x-amz-content-sha256`, ...) are dropped before signing; operation headers such as `X-Amz-Target` are kept.
- `none` injects nothing. A provider with `is_key_less: true` must use it.
- With `aws_sigv4`, a key that carries no credentials signs with the gateway's own AWS credential chain (instance role, environment, shared config), the same way Bedrock keys do. The caller chooses the operation through headers such as `X-Amz-Target`, so that role's permissions on the service are what every virtual key holder can exercise. Give such providers a dedicated key with scoped credentials or a role ARN.
- Every auth type except `none` and `aws_sigv4` requires the key to have a value, whether the key is created through the API or declared in config.json. Changing a provider's auth type to one of those is refused while any of its stored keys has no value (for example keys that held AWS credentials for `aws_sigv4`), so the relay never sends an unauthenticated request.

### `usage`

Paths are [gjson](https://github.com/tidwall/gjson) paths. Tokens and cost are read from the JSON response body; the model from the JSON request body.

| Field | Description |
| --- | --- |
| `model_path` | Request body path for the model name (default `model`). Used for governance model restrictions and the log row |
| `input_tokens_path`, `output_tokens_path`, `total_tokens_path` | Response body paths for tokens |
| `cost_path` | Response body path for a provider-reported USD cost; an array of numbers is summed |
| `cost_per_request` | Flat USD fee added to every billable call. A route may set `0` to waive the provider fee |
| `units_path` | gjson path of a billable quantity (pages, credits, text). Ignored when `units_measure` is `body_bytes` or `body_chars` |
| `units_source` | `response` (default): a count the API reports. `request`: what the caller sent, which per-character APIs bill on |
| `units_measure` | `value` (default): the number at the path. `chars`: the character count of the JSON string at the path (the body must be JSON). `body_bytes`: the byte length of the whole body. `body_chars`: the character count of the whole body, any content type |
| `cost_per_unit` | USD per unit. A route may set `0` to waive the provider's unit pricing |
| `units_block_size` | Bill per started block of this many raw units: `100` for an API priced per 100 characters (Comprehend Medical). Default exact |
| `units_minimum` | Least number of billed units once a quantity was read, e.g. `1`. Default `0` |
| `disable_optimistic_parsing` | Read only the configured paths |

**Per-unit pricing.** Most non-LLM APIs bill by quantity, and the quantity is in a different place for each:

| API | Bills per | Mapping |
| --- | --- | --- |
| AWS Textract | page | `units_path: DocumentMetadata.Pages`, `cost_per_unit: 0.0015` (response) |
| Tavily | API credit | `units_path: usage.credits`, `cost_per_unit: 0.008` (response; send `include_usage: true`) |
| AWS Translate | character of input, spaces included | `units_source: request`, `units_measure: chars`, `units_path: Text`, `cost_per_unit: 0.000015` |
| Azure TTS (neural voices) | character of SSML, markup included | `units_source: request`, `units_measure: body_chars`, `cost_per_unit: 0.000016` (the body is `application/ssml+xml`, so `chars` with a path cannot read it, and `body_bytes` would over-count multi-byte text) |

Cost per call is `billed units × cost_per_unit + cost_per_request + extracted cost`, where billed units is the raw quantity, rounded up to whole blocks (`ceil(quantity / units_block_size)`) when `units_block_size` is set, the way APIs priced per started 100-character block bill, and never below `units_minimum` when that is set. Request-side quantities count what the upstream itself bills on: a caller cannot send less text than it wants translated, and padding the text raises the upstream bill as much as the Bifrost charge. On the request side, a route that reads its quantity at `units_path` refuses with `400` a body that is not JSON, names a key twice, or whose charge would overflow, so a caller cannot be billed nothing by sending one; the caller's `Content-Type` is not consulted. On the response side, a quantity that is missing, negative or not JSON (unless the measure is `body_bytes` or `body_chars`, which read the whole body whatever its type) adds nothing. On an SSE stream a response-side quantity at a path is read per event and the last value reported wins (map a field that carries a running total). `body_bytes` and `body_chars` on the response side are counted as the reply is forwarded, so a streamed reply (SSE or not) is billed by its size exactly as a buffered one would be. A request-side quantity is known before the upstream answers and is kept on every path; an unframed stream (audio) reports it on its final chunk. Azure TTS Avatar bills per second of a batch job, which no synchronous relay can see; use a flat fee for it.

**Optimistic defaults.** With no mapping, Bifrost reads the shapes most APIs borrow: request `model`; response `usage.prompt_tokens` or `usage.input_tokens`, `usage.completion_tokens` or `usage.output_tokens`, `usage.total_tokens`; cost `usage.cost`. A root-level `cost` is never read by default, since on many APIs it is a product price rather than a bill. Naming any token path turns the optimistic token lookup off, so a half-mapped response is never topped up from a block you did not map. `disable_optimistic_parsing` also stops the default `model` lookup. Negative numbers are ignored. Bodies are scanned when their `Content-Type` is any JSON media type, including `application/x-amz-json-1.1`.

**`ignore_provider_cost`.** On a generic provider the Pricing tab's "ignore provider cost" switch drops only what the upstream reports (`cost_path`); the flat fee and unit pricing are yours and keep applying.

**What gets charged.** Every successful (2xx) call on a billable route reports usage, even when nothing could be read from the response, so it counts as one request against rate limits. Cost is `billed units × cost_per_unit + cost_per_request + extracted cost` (the formula above); budgets are charged when that is above zero. Non-2xx responses and non-billable routes report no usage, so they are never charged; as on every passthrough route, a call that names a model (by default the request's `model` field) still counts as one request against rate limits. Only `POST` is billable by default, with or without a route: `GET` and `HEAD` are usually polls and listings, `PUT` and `PATCH` update settings, and `DELETE` cleans up (an Azure avatar job, a Tavily crawl). Add a route with `billable: true` for an API that bills another method.

**Streams.** Each usage field keeps the last value any SSE event reported, so an API that reports input tokens on its first event and output tokens on its last is billed for both. Values are not summed: map fields that carry running totals (as OpenAI and Anthropic report them), not per-event increments. The one quantity read from a stream's body rather than its events is a response-side `body_bytes` or `body_chars`: the forwarded size is counted and charged when the stream ends, for SSE and unframed streams alike.

### `streaming`

| Field | Description |
| --- | --- |
| `paths` | Rooted segment globs (`/v1/stream/**`) that are always served as streams |
| `detect_from_accept_header` | Treat `Accept: text/event-stream` as a streaming request |
| `detect_from_body` | Treat `"stream": true` in a JSON body (or `?stream=true` on a `GET`) as a streaming request. Off by default: the streaming relay forwards a non-SSE reply unread, so on a provider billed from a path in the response a caller could otherwise add the flag and pay the flat fee alone (a size-based charge still applies). Turn it on for LLM-shaped upstreams, where the flag is the protocol |

Detection order: the matching route's `stream` flag, then `streaming.paths`, then the Accept header (when enabled), then a JSON body with `"stream": true` or `?stream=true` on a `GET` (when enabled). The path's wording is never a signal: a generic API with `stream` in a path usually answers with plain JSON, which the streaming relay would forward unread. SSE bodies are framed so usage on the final event is observed; any other stream (chunked JSON, binary audio) is forwarded unframed and reports the route's `cost_per_request` plus any request-side units when it completes, plus a response-side `body_bytes` or `body_chars` charge for the size forwarded; nothing is parsed from it. Set `stream: false` on a route whose reply you need parsed.

### `routes[]`

| Field | Description |
| --- | --- |
| `method` | `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD` |
| `path` | Rooted segment glob: `*` matches within a segment (`/jobs/*`), a trailing `/**` matches the prefix and everything below |
| `headers` | Request headers that must also match: header name (case-insensitive) to value glob, e.g. `{"X-Amz-Target": "Textract.Get*"}`. For APIs that send every operation to one path and name it in a header |
| `billable` | `false` relays the call without counting or charging it (status polls, listings); `true` counts it. Unset keeps the method default: only `POST` is billable |
| `stream` | Forces the streaming (`true`) or buffered (`false`) relay for this route |
| `usage` | Field-by-field override of the provider `usage` mapping |
| `job` | Makes the route the start of a provider-side job that is billed once it completes; see below |

The first matching route wins, so list the specific operation before its catch-all. A request matching no route uses the provider defaults and the method default for billing, so listing every operation of an API as routes (for example from an OpenAPI import) does not start charging its polls and listings.

**One path, many operations.** AWS JSON-protocol APIs (Textract, Translate, Comprehend) send every operation to `POST /` and name it in the `X-Amz-Target` header, so a route on method and path alone cannot tell them apart. Add `headers` to the route, as the Textract example above does: `AnalyzeDocument` at its own rate, result polls (`Get*`) free, job starts (`Start*`) at a flat fee, everything else at the base rate. The OpenAPI importer turns AWS path keys of the form `/#X-Amz-Target=Service.Operation` into these routes.

### Async jobs: `routes[].job`

Some operations start a job and return only an id; the billable quantity appears later, on a result the caller polls for. A route with a `job` block hands that job to Bifrost's job accounting sweeper, which polls the upstream itself and charges the job once, when it completes, against the budgets and rate limits the start call was subject to and with the key that started it. The start call still counts as one request and pays the route's own fee. The caller's own polls stay on their non-billable route.

```json
{ "method": "POST", "path": "/", "headers": { "X-Amz-Target": "Textract.StartDocumentAnalysis" },
  "usage": { "cost_per_unit": 0 },
  "job": {
    "id_path": "JobId",
    "poll": { "path": "/", "headers": { "X-Amz-Target": "Textract.GetDocumentAnalysis" },
              "body": "{\"JobId\":\"{{job.id}}\",\"MaxResults\":1}", "content_type": "application/x-amz-json-1.1" },
    "status_path": "JobStatus",
    "succeeded": ["SUCCEEDED", "PARTIAL_SUCCESS"],
    "failed": ["FAILED"],
    "timeout_seconds": 3600,
    "usage": { "units_path": "DocumentMetadata.Pages", "cost_per_unit": 0.0015 }
  } }
```

| Field | Description |
| --- | --- |
| `id_path` | gjson path of the job id in the start response |
| `poll` | The request that reports the job: `method` (default `POST`), rooted `path`, literal `headers`, literal `body`, `content_type` (default `application/json`). `{{job.id}}` is replaced with the job id wherever it appears |
| `status_path` | gjson path of the status in the poll response |
| `succeeded`, `failed` | Status values, compared case-insensitively, that end the job with work to bill or at no charge |
| `interval_seconds` | Seconds until the first poll (default 30). Later polls follow the sweeper's own 30-second tick, backing off to two and five minutes after 20 and 40 attempts |
| `timeout_seconds` | Stop polling after this long (default 3600); the job is recorded as unpriced with reason `generic_job_timeout` |
| `usage` | Mapping applied to the terminal poll response, over the route's and the provider's |

How it settles: the mapping, status words and poll request are captured on the job row when the job starts, so editing the provider later does not change how a running job is billed. A terminal `succeeded` response is priced like a buffered reply (`units × cost_per_unit + cost_per_request + extracted cost`, with rounding) and written as a cost row nested under the start call's log row, with the job id, status, units and rates in its `params.job_accounting`. A `failed` status settles at zero. A poll the upstream answers with 404 or 410 parks the job as gone, a 401 or 403 as access denied, a 4xx the upstream will never accept as rejected; a 5xx or a transport error is retried. A job the caller starts and never reads is still billed, because Bifrost does the reading. Settlement is at least once with a per-job dedupe, the same guarantee batches and video jobs have. A start the upstream answers with a job it already has (an idempotent retry, such as Textract's `ClientRequestToken`) is billed once while that job is still open for the same key; an id an API lets callers reuse after the old job is gone (Azure batch synthesis) is billed again, since the earlier job has settled by then.

### `strict_routes`

With `strict_routes: true`, a request that matches no `routes[]` entry is refused with `404` before anything is forwarded, so the routes list doubles as an allowlist. Like the path guard and an unknown provider name, this refusal is answered before dispatch, so it runs no plugins and writes no log row. Without it, routes are overrides and every operation is relayed.

### Importing from an OpenAPI document

On the Passthrough tab, **Import from an OpenAPI document** accepts a pasted document, an uploaded file, or a URL fetched by your browser. Its operations become routes (a path parameter becomes `*` wherever it sits, so `/files/{id}.json` becomes `/files/*.json`, and glob characters in literal text are escaped), the auth type and header name come from the document's top-level security requirement (the first alternative that names a single supported scheme, or the only scheme when the document declares just one), and `strict_routes` is switched on. An operation that sets its own `security` is read under that requirement instead, and a public operation (`security: []`) is left out of the auth choice. Public operations are still imported as routes, so remove any you do not want allowed under `strict_routes`. Three cases leave fields as they were, with a warning in the import summary: operations that require different schemes leave the auth unchanged, since one provider applies one auth; a document with several schemes and no top-level requirement that picks one leaves the auth unchanged; and a document whose path items sit behind `$ref` imports only the inline ones and leaves `strict_routes` unchanged. In those cases set the auth yourself, add the skipped routes, and switch `strict_routes` on once the list is complete, or calls to the skipped operations are relayed without an allowlist. The server URL is shown as a hint for the Network tab. The document is parsed in the browser and never sent to or stored by Bifrost; review the fields it filled in and save them like any others. The URL option works only when the vendor allows cross-origin reads of the file; otherwise paste or upload it.

## Making requests

```bash
# Tavily search through Bifrost, authenticated with a Bifrost virtual key.
# include_usage makes Tavily report usage.credits, which the mapping above bills;
# without it the call is counted but costs nothing.
curl -X POST http://localhost:8080/passthrough/tavily/search \
  -H "Authorization: Bearer sk-bf-..." \
  -H "Content-Type: application/json" \
  -d '{"query": "bifrost ai gateway", "max_results": 3, "include_usage": true}'

# AWS Textract, SigV4-signed by Bifrost
curl -X POST http://localhost:8080/passthrough/textract/ \
  -H "Authorization: Bearer sk-bf-..." \
  -H "Content-Type: application/x-amz-json-1.1" \
  -H "X-Amz-Target: Textract.DetectDocumentText" \
  -d '{"Document": {"Bytes": "<base64>"}}'
```

The response carries the upstream headers, minus the exclusions in the overview and any header that echoes a query-auth key, plus `x-bifrost-provider` and `x-bifrost-request-id`. `x-bifrost-passthrough-path` is added only when `client.extra_fields_placement` is `headers`; with the default, `body`, it is not sent, since a relayed body carries no Bifrost fields. The query string is forwarded unchanged (the auth query parameter, when configured, is stripped from the caller's query and re-added with the selected key).

Only custom providers with the generic base type are served by `/passthrough/{provider}`. A standard provider name, or a custom provider of another base type, is a `404`; standard providers keep their own passthrough routes (see [Passthrough](./passthrough)).

## Governance and logs

- **Virtual keys** scope access by provider name, so a key may allow `tavily` and not `textract`. Budgets and rate limits attach per provider as for any other.
- A virtual key that **restricts models** refuses a passthrough call that names no model. Non-LLM APIs rarely do, so allow `*` on generic providers, or map `usage.model_path` to a request field that should act as the model.
- The model is **read from the caller's body** at `usage.model_path` (default `model`), and only there: a caller can name any value in that field. Treat model restrictions on generic providers as routing hints, not access control; provider-level allowlists on the virtual key are the access control. With `disable_optimistic_parsing` and no `model_path`, no model is read, so a virtual key that restricts models refuses every call on the provider; give such keys `*` on generic providers.
- **Logs** keep a generic relay as a `passthrough` row. With content logging enabled, JSON request bodies are stored, multipart requests are summarized, and other request content types are not stored. Text response bodies are stored even when they are not JSON; binary responses become size placeholders. Tokens and cost read through the usage mapping appear on the row.

## Security notes

- The upstream host is pinned: a path that would change the authority (`//host`, `@host`, a scheme) is refused before dispatch.
- Caller `authorization`, `api-key`, `x-api-key`, `x-goog-api-key`, cookies and every `x-bf-*` header are dropped; the header or query parameter named by `auth` is replaced with the configured key.
- `base_url` is validated like any provider URL (`allow_private_network` governs private targets).
- Redirects are never followed: a 3xx from the upstream is returned to the caller as is, so the injected key never reaches a host the upstream named.
- Transport errors name the upstream host and path but never the query string, which for query auth carries the key.
- Response headers are scrubbed of a query-auth key before they reach the caller or the log row: a `Location` (or any other header) that echoes the request query loses the auth parameter.
- With query auth, the caller's own copy of the auth parameter is removed and every other query segment is forwarded byte for byte, in its original order and encoding, so signed or compared query strings survive. Bifrost scans a query that contains the configured parameter name or a `%`; during that scan, a parameter name that cannot be decoded, or a `;` separator, is refused with `400` rather than relayed, since the caller's credential could be hiding in it. A query containing neither cannot carry the credential and is forwarded without that check.
- Beyond `authorization`, `api-key`, `x-api-key`, `x-goog-api-key` and cookies, every caller header whose name marks it as a credential (`*-token`, `*secret*`, `*api-key*`, `*jwt*`, `cf-access-*`, `x-amzn-oidc-*`, `ocp-apim-subscription-key`, `subscription-key`, `x-functions-key`) is dropped, so a caller cannot route their own upstream account through the provider. Non-credential headers such as `x-idempotency-key` and `x-amz-target` are forwarded.
- The buffered relay caps a response at 64 MiB; use a streaming route for anything larger.
- A caller cannot choose the streaming relay unless the operator allows it (`detect_from_body`, `detect_from_accept_header`), so a response-billed call cannot be turned into a flat-fee call by adding `"stream": true`.
- Request-side quantities should be `chars` or `body_chars` of what the upstream processes, never a number the caller supplies (`value` on a request field), since the caller would then set their own bill.
