## Overview

A **generic passthrough provider** is a custom provider whose `base_provider_type` is `generic`. It is a raw HTTP relay: Bifrost forwards the request bytes untouched to the API you configured and returns the upstream status, headers and body unchanged. Nothing about the request has to look like an LLM call.

What Bifrost still does on every call:

- Selects a key from the provider's key pool and injects it the way the API expects (bearer, custom header, query parameter, HTTP basic, or AWS Signature V4). Caller credentials are stripped.
- Pins the upstream host to the provider's `network_config.base_url`.
- Runs the plugin pipeline, writes a log row with the raw request and response bodies, and reports usage so governance counts the request against rate limits and charges budgets.
- Optionally confines the provider to the operations you listed (`strict_routes`), a list you can import from the API's OpenAPI document in the UI.

Each API is its own provider. The first segment after `/passthrough/` selects it:

```
POST /passthrough/tavily/search                  → https://api.tavily.com/search
POST /passthrough/textract/                      → https://textract.us-east-1.amazonaws.com/   (SigV4)
POST /passthrough/azure-tts/cognitiveservices/v1 → https://eastus.tts.speech.microsoft.com/cognitiveservices/v1
```

<Warning>
**Authenticate to Bifrost with your Bifrost virtual key, not the upstream API key.** Caller `authorization`, `x-api-key` and similar headers never reach the upstream; Bifrost always injects the key it selects from the provider's configured keys.
</Warning>

## Configuration

<Tabs>
<Tab title="Web UI">
1. Go to **Providers** and choose **Add New Provider → Custom provider...**
2. Set a name (this becomes the route segment), choose **generic** as the base format, and enter the API's base URL.
3. Pick the **Auth type** and fill its fields (header name for `header`, query parameter for `query`, service and region for `aws_sigv4`).
4. Save, then add a key. For `aws_sigv4` the key carries AWS credentials (access key, secret key, region, or a role ARN) instead of a value.
5. Open the provider's **Passthrough** tab to set usage and cost mapping, streaming rules and per-route overrides, or import them from the API's OpenAPI document.
</Tab>
<Tab title="API">
```bash
curl -X POST http://localhost:8080/api/providers \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "tavily",
    "network_config": { "base_url": "https://api.tavily.com" },
    "custom_provider_config": {
      "base_provider_type": "generic",
      "generic_config": {
        "auth": { "type": "bearer" },
        "usage": { "cost_per_request": 0.008 }
      }
    }
  }'

curl -X POST http://localhost:8080/api/providers/tavily/keys \
  -H "Content-Type: application/json" \
  -d '{ "name": "tavily-prod", "value": "tvly-...", "weight": 1, "models": ["*"] }'
```
</Tab>

`network_config.base_url` is required. `allowed_requests` defaults to `passthrough` and `passthrough_stream`; no typed operation can be enabled on a generic provider, and `request_path_overrides` does not apply.

## `generic_config` reference

### `auth`

| Field | Applies to | Description |
| --- | --- | --- |
| `type` | all | `bearer` (default), `header`, `query`, `basic`, `aws_sigv4`, `none` |
| `header_name` | `header` | Header that carries the key, e.g. `x-api-key` or `Ocp-Apim-Subscription-Key` |
| `value_prefix` | `header` | Literal prefix placed before the key value, e.g. `Token ` |
| `query_param` | `query` | Query parameter that carries the key, e.g. `api_key` |
| `aws.service` | `aws_sigv4` | SigV4 signing name, e.g. `textract`, `translate`, `execute-api` |
| `aws.region` | `aws_sigv4` | AWS region; falls back to the key's `bedrock_key_config.region` |

- `bearer` sends `Authorization: Bearer <key>`; `basic` sends `Authorization: Basic base64(<key>)` where the key value is `user:password`.
- `aws_sigv4` signs the request with the key's `bedrock_key_config` credentials (static keys, an assumed role, or the default AWS credential chain when the key holds none). Caller signature headers (`x-amz-date`, `x-amz-security-token`, `x-amz-content-sha256`, ...) are dropped before signing; operation headers such as `X-Amz-Target` are kept.
- `none` injects nothing. A provider with `is_key_less: true` must use it.
- With `aws_sigv4`, a key that carries no credentials signs with the gateway's own AWS credential chain (instance role, environment, shared config), the same way Bedrock keys do. The caller chooses the operation through headers such as `X-Amz-Target`, so that role's permissions on the service are what every virtual key holder can exercise. Give such providers a dedicated key with scoped credentials or a role ARN.
- Every auth type except `none` and `aws_sigv4` requires the key to have a value, whether the key is created through the API or declared in config.json. Changing a provider's auth type to one of those is refused while any of its stored keys has no value (for example keys that held AWS credentials for `aws_sigv4`), so the relay never sends an unauthenticated request.

### `usage`

Paths are [gjson](https://github.com/tidwall/gjson) paths. Tokens and cost are read from the JSON response body; the model from the JSON request body.

| Field | Description |
| --- | --- |
| `model_path` | Request body path for the model name (default `model`). Used for governance model restrictions and the log row |
| `input_tokens_path`, `output_tokens_path`, `total_tokens_path` | Response body paths for tokens |
| `cost_path` | Response body path for a provider-reported USD cost; an array of numbers is summed |
| `cost_per_request` | Flat USD fee added to every billable call. A route may set `0` to waive the provider fee |
| `units_path` | gjson path of a billable quantity (pages, credits, text). Ignored when `units_measure` is `body_bytes` |
| `units_source` | `response` (default): a count the API reports. `request`: what the caller sent, which per-character APIs bill on |
| `units_measure` | `value` (default): the number at the path. `chars`: the character count of the string at the path. `body_bytes`: the byte length of the whole body |
| `cost_per_unit` | USD per unit. A route may set `0` to waive the provider's unit pricing |
| `disable_optimistic_parsing` | Read only the configured paths |

**Per-unit pricing.** Most non-LLM APIs bill by quantity, and the quantity is in a different place for each:

| API | Bills per | Mapping |
| --- | --- | --- |
| AWS Textract | page | `units_path: DocumentMetadata.Pages`, `cost_per_unit: 0.0015` (response) |
| Tavily | API credit | `units_path: usage.credits`, `cost_per_unit: 0.008` (response; send `include_usage: true`) |
| AWS Translate | character of input, spaces included | `units_source: request`, `units_measure: chars`, `units_path: Text`, `cost_per_unit: 0.000015` |
| Azure TTS (neural voices) | character of SSML | `units_source: request`, `units_measure: body_bytes`, `cost_per_unit: 0.000016` |

Cost per call is `units × cost_per_unit + cost_per_request + extracted cost`. Request-side quantities count what the upstream itself bills on: a caller cannot send less text than it wants translated, and padding the text raises the upstream bill as much as the Bifrost charge. A quantity that is missing, negative or not JSON (unless the measure is `body_bytes`) adds nothing. On an SSE stream a response-side quantity is read per event and the last value reported wins (map a field that carries a running total); `body_bytes` on the response side is read from buffered responses only. A request-side quantity is known before the upstream answers and is kept on every path; an unframed stream (audio) reports it on its final chunk. Azure TTS Avatar bills per second of a batch job, which no synchronous relay can see; use a flat fee for it.

**Optimistic defaults.** With no mapping, Bifrost reads the shapes most APIs borrow: request `model`; response `usage.prompt_tokens` or `usage.input_tokens`, `usage.completion_tokens` or `usage.output_tokens`, `usage.total_tokens`; cost `usage.cost`. A root-level `cost` is never read by default, since on many APIs it is a product price rather than a bill. Naming any token path turns the optimistic token lookup off, so a half-mapped response is never topped up from a block you did not map. `disable_optimistic_parsing` also stops the default `model` lookup. Negative numbers are ignored. Bodies are scanned when their `Content-Type` is any JSON media type, including `application/x-amz-json-1.1`.

**`ignore_provider_cost`.** On a generic provider the Pricing tab's "ignore provider cost" switch drops only what the upstream reports (`cost_path`); the flat fee and unit pricing are yours and keep applying.

**What gets charged.** Every successful (2xx) call on a billable route reports usage, even when nothing could be read from the response, so it counts as one request against rate limits. Cost is `extracted cost + cost_per_request`; budgets are charged when that is above zero. Non-2xx responses and non-billable routes report no usage, so they are never charged; as on every passthrough route, a call that names a model (by default the request's `model` field) still counts as one request against rate limits. `GET` and `HEAD` are not billable by default, with or without a route (they are usually polls and listings); add a route with `billable: true` to count them.

**Streams.** Each usage field keeps the last value any SSE event reported, so an API that reports input tokens on its first event and output tokens on its last is billed for both. Values are not summed: map fields that carry running totals (as OpenAI and Anthropic report them), not per-event increments.

### `streaming`

| Field | Description |
| --- | --- |
| `paths` | Rooted segment globs (`/v1/stream/**`) that are always served as streams |
| `detect_from_accept_header` | Treat `Accept: text/event-stream` as a streaming request |

Detection order: the matching route's `stream` flag, then `streaming.paths`, then the Accept header (when enabled), then a JSON body with `"stream": true`. The path's wording is never a signal: a generic API with `stream` in a path usually answers with plain JSON, which the streaming relay would forward unread. SSE bodies are framed so usage on the final event is observed; any other stream (chunked JSON, binary audio) is forwarded unframed and reports the route's `cost_per_request` plus any request-side units when it completes, never anything read from the response. Set `stream: false` on a route whose reply you need parsed.

### `routes[]`

| Field | Description |
| --- | --- |
| `method` | `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD` |
| `path` | Rooted segment glob: `*` matches within a segment (`/jobs/*`), a trailing `/**` matches the prefix and everything below |
| `billable` | `false` relays the call without counting or charging it (status polls, listings); `true` counts it. Unset keeps the method default: `GET` and `HEAD` are not billable, every other method is |
| `stream` | Forces the streaming (`true`) or buffered (`false`) relay for this route |
| `usage` | Field-by-field override of the provider `usage` mapping |

The first matching route wins. A request matching no route uses the provider defaults and the method default for billing, so listing every operation of an API as routes (for example from an OpenAPI import) does not start charging its polls and listings.

### `strict_routes`

With `strict_routes: true`, a request that matches no `routes[]` entry is refused with `404` before anything is forwarded, so the routes list doubles as an allowlist. Without it, routes are overrides and every operation is relayed.

### Importing from an OpenAPI document

On the Passthrough tab, **Import from an OpenAPI document** accepts a pasted document, an uploaded file, or a URL fetched by your browser. Its operations become routes (path parameters such as `{id}` become `*`), its first security scheme sets the auth type and header name, and `strict_routes` is switched on. The server URL is shown as a hint for the Network tab. The document is parsed in the browser and never sent to or stored by Bifrost; review the fields it filled in and save them like any others. The URL option works only when the vendor allows cross-origin reads of the file; otherwise paste or upload it.

## Making requests

```bash
# Tavily search through Bifrost, authenticated with a Bifrost virtual key
curl -X POST http://localhost:8080/passthrough/tavily/search \
  -H "Authorization: Bearer sk-bf-..." \
  -H "Content-Type: application/json" \
  -d '{"query": "bifrost ai gateway", "max_results": 3}'

# AWS Textract, SigV4-signed by Bifrost
curl -X POST http://localhost:8080/passthrough/textract/ \
  -H "Authorization: Bearer sk-bf-..." \
  -H "Content-Type: application/x-amz-json-1.1" \
  -H "X-Amz-Target: Textract.DetectDocumentText" \
  -d '{"Document": {"Bytes": "<base64>"}}'
```

The response carries the upstream headers plus `x-bifrost-provider`, `x-bifrost-request-id` and `x-bifrost-passthrough-path`. The query string is forwarded unchanged (the auth query parameter, when configured, is stripped from the caller's query and re-added with the selected key).

Only custom providers with the generic base type are served by `/passthrough/{provider}`. A standard provider name, or a custom provider of another base type, is a `404`; standard providers keep their own passthrough routes (see [Passthrough](./passthrough)).

## Governance and logs

- **Virtual keys** scope access by provider name, so a key may allow `tavily` and not `textract`. Budgets and rate limits attach per provider as for any other.
- A virtual key that **restricts models** refuses a passthrough call that names no model. Non-LLM APIs rarely do, so allow `*` on generic providers, or map `usage.model_path` to a request field that should act as the model.
- The model is **read from the caller's body** at `usage.model_path` (default `model`), and only there: a caller can name any value in that field. Treat model restrictions on generic providers as routing hints, not access control; provider-level allowlists on the virtual key are the access control. With `disable_optimistic_parsing` and no `model_path`, no model is read and model restrictions do not apply.
- **Logs** keep a generic relay as a `passthrough` row with the raw JSON request and response bodies. Multipart bodies are summarized; other content types are not stored. Tokens and cost read through the usage mapping appear on the row.

## Security notes

- The upstream host is pinned: a path that would change the authority (`//host`, `@host`, a scheme) is refused before dispatch.
- Caller `authorization`, `api-key`, `x-api-key`, `x-goog-api-key`, cookies and every `x-bf-*` header are dropped; the header or query parameter named by `auth` is replaced with the configured key.
- `base_url` is validated like any provider URL (`allow_private_network` governs private targets).
- Redirects are never followed: a 3xx from the upstream is returned to the caller as is, so the injected key never reaches a host the upstream named.
- Transport errors name the upstream host and path but never the query string, which for query auth carries the key.
- Response headers are scrubbed of a query-auth key before they reach the caller or the log row: a `Location` (or any other header) that echoes the request query loses the auth parameter.
- With query auth, a request whose query string cannot be parsed is refused with 400 rather than relayed, since the caller's own credential could be hiding in it.
- The buffered relay caps a response at 64 MiB; use a streaming route for anything larger.
