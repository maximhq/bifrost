## Overview

Passthrough integrations let you call provider-native API paths and payloads through Bifrost without route-level request/response conversion.

When you use passthrough endpoints, the request still flows through Bifrost core logic. You keep Bifrost features such as logging and observability while sending provider-native paths and bodies.

---

## Endpoints

- `/openai_passthrough`
  Default provider: `openai`
- `/anthropic_passthrough`
  Default provider: `anthropic`
- `/azure_passthrough`
  Default provider: `azure`
- `/genai_passthrough`
  Default provider: `gemini` (with automatic Vertex detection for clients configured to use Vertex)
- `/bedrock_passthrough`
  Default provider: `bedrock` (restricted to three operations, see [Bedrock Passthrough](#bedrock-passthrough))
- `/sagemaker_passthrough`
  Default provider: `sagemaker` (restricted to endpoint invocations, see [SageMaker Passthrough](#sagemaker-passthrough))

---

## How It Works

1. Send your request to a passthrough endpoint (OpenAI, Anthropic, Azure, GenAI, Bedrock, or SageMaker passthrough).
2. The integration strips the passthrough prefix and forwards the remaining provider-native path/body.
3. Bifrost resolves upstream authentication:
   - **Gateway-managed key (default):** Client-supplied credentials (`authorization`, `api-key`, `x-api-key`, `x-goog-api-key`) are stripped, and Bifrost selects a key from its own key config for the resolved provider and model.
   - **Supported caller OAuth:** An Anthropic OAuth bearer token or OpenAI JWT bearer token is forwarded to its native HTTPS provider, and Bifrost skips provider-key selection for that request.
   - **Direct provider credential (explicit opt-in):** When the server allows direct API keys and the request includes `x-bf-direct-key: true`, Bifrost uses the caller's provider credential instead of its configured key pool.
4. Bifrost handles provider execution through core inference and plugin pipelines.
5. Response status, headers, and body are returned as passthrough output (for both stream and non-stream requests).

<Warning>
**A provider API key is not passed through by default.** In the standard flow, authenticate to Bifrost with a Bifrost virtual key and let Bifrost select the upstream provider key. General provider-credential forwarding requires both the server-side `allow_direct_keys` setting and `x-bf-direct-key: true` on the request.
</Warning>

<Note>
When the URL path names a model (for example `models/{model}` or a deployment path), Bifrost uses that model. Otherwise, for JSON bodies, it reads the model from the top-level `model` key, the same key the provider reads. Virtual-key model restrictions apply to whichever model was resolved. A JSON body must carry that key at most once, spelled exactly `model` (lowercase), with a string value; a body that repeats it (in any letter case), spells it differently, gives it a non-string value, or is not valid JSON while sent as `application/json` is rejected with `400`. Bodies without a `model` key and multipart bodies are unaffected.
</Note>

<Note>
Without Edge, Claude Code OAuth sign-in (`Authorization: Bearer sk-ant-oat…`) can use the regular `/anthropic` route, where Bifrost preserves the provider-native request and forwards the token instead of selecting a key. With Bifrost Edge, use **subscription pass-through** for native-credential inference: Edge preserves the credential and catalog, rewrites captured inference to `/anthropic_passthrough`, and enables the direct-key request path. **Require Anthropic login** alone does not select this route. See [Edge routing modes](/edge/supported-applications#edge-routing-modes).
</Note>

### Caller credential forwarding

Recognized subscription credentials are forwarded only when all of the following are true:

- The credential is a recognized Anthropic OAuth bearer token or OpenAI JWT bearer token.
- The request resolves to the matching native provider. An Anthropic token is never forwarded to Bedrock, Vertex, Azure, or another provider.
- The upstream is HTTPS. A caller credential is not forwarded to a plaintext `http://` upstream override.

When Bifrost inference authentication requires a separate gateway identity, send the Bifrost virtual key through `x-bf-vk`; do not replace the provider OAuth token in `Authorization`. Bifrost Edge manages the gateway identity and native application credential separately.

### Bifrost Edge subscription pass-through

For supported applications, Edge configures the direct-provider-credential path automatically:

1. Edge keeps the application's native credential and native model catalog.
2. Edge routes captured inference to the matching Bifrost passthrough endpoint.
3. Edge adds `x-bf-direct-key: true` and authenticates to Bifrost separately with the selected virtual key or signed-in agent identity.
4. Bifrost attributes the request to the resolved user and source application, runs the plugin pipeline, records logs according to logging policy, and forwards the native credential only to the matching provider.

This mode requires **Allow Direct API Keys** in Bifrost security settings. It bypasses Bifrost's configured provider-key pool, not the Bifrost gateway. Key selection and key rotation/load balancing do not apply to the caller's native credential. Model routing, inference routing to another provider, and cross-provider fallbacks are not supported.

## Provider Selection Rules

### OpenAI Passthrough

- Uses `openai` as the default provider.

### Anthropic Passthrough

- Uses `anthropic` as the default provider.

### Azure Passthrough

- Uses `azure` as the default provider.
- Requires an Azure key with `endpoint` configured.
- **`api-version` handling varies by route:**
  - `/openai/deployments/` routes: if the caller omits `api-version`, Bifrost injects a default (`2025-04-01-preview`). Pass your own `api-version` to override — for example, to pin to a GA version or use a specific preview version.

### Bedrock Passthrough

- Uses `bedrock` as the default provider.
- **Not a general AWS proxy.** Bifrost forwards only the Bedrock operations it has no native route for, and refuses every other path, method or malformed identifier with a `400` before any request is built:

  | Operation | Method and path (after `/bedrock_passthrough`) | AWS service host |
  |---|---|---|
  | InvokeAgent | `POST /agents/{agentId}/agentAliases/{agentAliasId}/sessions/{sessionId}/text` | `bedrock-agent-runtime` |
  | Retrieve (knowledge base) | `POST /knowledgebases/{knowledgeBaseId}/retrieve` | `bedrock-agent-runtime` |
  | ApplyGuardrail | `POST /guardrail/{guardrailId}/version/{version}/apply` | `bedrock-runtime` |

- Identifiers follow the character sets AWS documents for each parameter: agent, alias, knowledge-base and guardrail ids are alphanumeric, a session id may also contain `.`, `_`, `:` and `-` (but never consists only of dots), and a guardrail version is `DRAFT` or a number from 1 to 8 digits. An ARN is not accepted in place of an id.
- The host comes from the key's `region` (or its `endpoints` overrides). Credentials in the incoming request are never forwarded. `InvokeAgent` and `Retrieve` are always signed with the key's AWS credentials (SigV4, service `bedrock`), because AWS does not accept Bedrock API keys for Agents Runtime operations: a key that holds only an API key is refused with a `400` for those two operations, so select a key that has an access key and secret key or a role (for example with `x-bf-api-key`). `ApplyGuardrail` sends the key's Bedrock API key as a bearer token when it has one, and is SigV4-signed otherwise.
- The AWS status and body come back unchanged, together with the response headers Bifrost forwards, including `Content-Type` and `X-Amzn-*` such as `X-Amzn-Errortype` and `X-Amzn-Requestid`. Transport-level headers (for example `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `Connection` and `Date`) and credential-bearing ones (`Set-Cookie`, anything that looks like an API key or secret, and `X-Amzn-Oidc-*`) are removed, so an upstream `ResourceNotFoundException` still reaches the caller with its exception type. `InvokeAgent` is forwarded to the client as AWS produces it, so a long agent run is not buffered and is not bound by the gateway's whole-response timeout (only a stalled connection ends it, via the stream idle timeout). `Retrieve` and `ApplyGuardrail` are returned as a single response.

### SageMaker Passthrough

- Uses `sagemaker` as the default provider.
- Covers containers the [SageMaker provider](../providers/supported-providers/sagemaker) has no native route for, such as TEI, LMI's native format and custom images. The request body and the response are whatever the container defines.
- **Not a general AWS proxy.** Only these two operations are forwarded. Any other method, path or malformed name is refused with a `400` before anything reaches AWS:

  | Operation | Method and path (after `/sagemaker_passthrough`) |
  |---|---|
  | InvokeEndpoint | `POST /endpoints/{endpoint}[/inference-components/{component}]/invocations` |
  | InvokeEndpointWithResponseStream | `POST /endpoints/{endpoint}[/inference-components/{component}]/invocations-response-stream` |

- Endpoint and component names follow SageMaker's naming rules (up to 63 letters, digits and hyphens, starting and ending with a letter or digit). The inference component is sent to AWS in the `X-Amzn-SageMaker-Inference-Component` header, since `/invocations` has no inference-component path form.
- **The endpoint in the path is the model.** Bifrost uses `{endpoint}` (or `{endpoint}/{component}`) for key selection, governance and logs, in the same shape as a [SageMaker model id](../providers/supported-providers/sagemaker#model-ids) without the region prefix. Key `models` lists and virtual-key model restrictions apply to it. A `model` field in the body is the container's own served name and is never used for routing.
- The runtime host comes from the key's `region` (or its `endpoints.runtime` override). Requests are always SigV4-signed with the key's AWS credentials. A key that holds only a bearer token is refused with a `400`, so select a key with an access key and secret key, a role, or inherited credentials (for example with `x-bf-api-key`).
- Only these client headers are forwarded: `Content-Type`, `Accept`, and the SageMaker headers `X-Amzn-SageMaker-Custom-Attributes`, `-Target-Model`, `-Target-Variant`, `-Target-Container-Hostname`, `-Inference-Id`, `-Enable-Explanations` and `-Session-Id`. `Authorization`, `Host` and every other `x-amz-*` header are dropped.
- The container's status code, headers and body come back unchanged, including non-2xx container errors.
- **Streaming:** Bifrost unpacks AWS's event-stream framing and relays only the payload bytes, so the container's own format (SSE, JSON lines, and so on) reaches any HTTP client unchanged. `X-Amzn-SageMaker-Content-Type` is returned as the response `Content-Type`. A `ModelStreamError` or `InternalStreamFailure` ends the stream with an error, and a non-200 answer from SageMaker is returned as plain JSON. Token usage is not parsed, because the payload format is unknown to Bifrost.

### GenAI Passthrough

- Uses `gemini` by default.
- Automatically switches to `vertex` when Vertex patterns are detected, such as:
  - URL path containing `/projects/{PROJECT_ID}/locations/{LOCATION}/`
  - Request body `model` containing a Vertex resource path
  - OAuth token pattern typically used for Vertex (`Bearer ya29...`)

## Usage Examples

### OpenAI Passthrough

<Tabs group="openai-passthrough">
<Tab title="Python SDK">

```python
import openai

client = openai.OpenAI(
    base_url="http://localhost:8080/openai_passthrough/v1",
    api_key="<YOUR-BIFROST-VIRTUAL-KEY>"  # Replace with your actual Bifrost virtual key.
)

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hello from passthrough"}]
)

print(response.choices[0].message.content)
```

</Tab>
<Tab title="cURL">

```bash
curl -X POST "http://localhost:8080/openai_passthrough/v1/chat/completions" \
  -H "content-type: application/json" \
  -H "authorization: Bearer <YOUR-BIFROST-VIRTUAL-KEY>" \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role":"user","content":"hello from passthrough"}]
  }'
```

</Tab>
</Tabs>

## Notes

- Use passthrough when you need a provider endpoint that is not directly supported by Bifrost integration routes yet.
- **Provider key selection is normally done by Bifrost, not by the caller.** The client's `authorization`, `api-key`, `x-api-key`, and `x-goog-api-key` headers are dropped before the request leaves Bifrost, and the upstream auth header is set from the Bifrost key config. Recognized subscription OAuth/JWT and explicitly enabled direct keys are the caller-auth exceptions described above.
- [Direct API keys](../providers/request-options#direct-api-key) need both the server-side `allow_direct_keys` setting and a per-request `x-bf-direct-key: true` header. Without both, a raw provider key in the request is not used as the upstream credential.
- For Azure `/openai/deployments/` routes, Bifrost injects `api-version=2025-04-01-preview` when the caller does not supply one. Supply your own `api-version` query parameter to use a different version (e.g. `2024-10-21` for the latest GA, or a newer preview).
