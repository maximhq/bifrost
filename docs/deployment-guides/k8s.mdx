The Bifrost Terraform module can create resources for ECS, EKS, GKE, Cloud Run, AKS, Azure Container Instances, or an existing Kubernetes cluster. Use [Bifrost Deployment Requirements](/deployment-guides/runtime-contract) to choose the storage, secrets, networking, and replica configuration passed to the module.

<Warning>
Terraform support means the repository contains a module and mocked provider tests. It does not mean every target is continuously deployed into a live cloud account. Check the [deployment support matrix](/deployment-guides/overview) before treating a target as production-qualified.
</Warning>

## Supported module targets

| Cloud | `service` | Intended deployment |
|---|---|---|
| AWS | `ecs` | ECS Fargate; local task storage is ephemeral, so durable use needs persistent `/app/data` or external PostgreSQL |
| AWS | `eks` | EKS and Kubernetes resources; the module currently creates a PVC for every deployment; HPA |
| GCP | `gke` | GKE and Kubernetes resources; the module currently creates a PVC for every deployment; HPA |
| GCP | `cloud-run` | Cloud Run v2; durable use needs external stores and OSS DB-managed config must remain at one instance |
| Azure | `aks` | AKS and Kubernetes resources; the module currently creates a PVC for every deployment; HPA |
| Azure | `aci` | Single public Azure Container Instance for evaluation; module filesystem is ephemeral and the module does not terminate TLS |
| Kubernetes | `deployment` | Existing Kubernetes cluster; the module currently creates a PVC for every deployment; HPA and Ingress |

## Deployment steps

The example below deploys the Terraform module to ECS. The repository also contains complete examples for GKE, AKS, and an existing Kubernetes cluster under `terraform/examples`. EKS, Cloud Run, and ACI are supported module targets but do not currently have separate example directories.

### Step 1: Copy the example

```bash
git clone https://github.com/maximhq/bifrost.git
cd bifrost/terraform/examples/aws-ecs
cp terraform.tfvars.example terraform.tfvars
```

### Step 2: Configure Bifrost

Create `config.json` using the [PostgreSQL example](/deployment-guides/runtime-contract#postgresql). In `terraform.tfvars`, uncomment `config_json_file`, replace the existing `config_store`, `logs_store`, and sample `providers_config` blocks with `null`, and set the deployment values as follows:

```hcl
region           = "<AWS_REGION>"
image_tag        = "<BIFROST_VERSION>"
config_json_file = "./config.json"
config_store      = null
logs_store        = null
providers_config  = null

desired_count        = 1
create_load_balancer = true
enable_autoscaling   = false
```

Replace every angle-bracket placeholder. Setting the three override variables to `null` is important: non-null Terraform variables take precedence over the corresponding sections in `config.json`. Add real provider configuration to `config.json` or replace `providers_config = null` with the provider map you intend to deploy.

The supplied example defaults to SQLite and multiple replicas; do not retain that combination. Bifrost does not need durable `/app/data` storage when both stores use PostgreSQL, although the current EKS, GKE, AKS, and generic Kubernetes Terraform submodules still create a PVC. Review that extra resource in the plan.

### Step 3: Review and apply

The checked-out example uses the module from the same repository. If you copy the module block into another repository, pin its `source` to a released Terraform tag. Keep `image_tag` pinned to the Bifrost version you tested.

```bash
terraform init
terraform validate
terraform plan -out=bifrost.tfplan
terraform apply bifrost.tfplan
```

Do not apply until the plan contains only resources that your team intends Terraform to manage.

### Step 4: Verify

```bash
terraform output
curl --fail --show-error "https://<BIFROST_HOST>/health"
```

Use `terraform destroy` only when you intend to remove every resource owned by this example state.

## Secrets and Terraform state

Terraform stores resource attributes in state. Passing provider keys, database passwords, an encryption key, or a complete `config.json` through Terraform can therefore place those values in state even when the cloud resource is a secret manager.

For production:

- Use an encrypted remote state backend with locking, versioning, and a narrow IAM policy.
- Restrict access to plans and CI logs.
- Prefer workload identity and secret references where the target supports them.
- Rotate any credential that was exposed through an unsecured local state file.
- Never commit `terraform.tfstate`, plan files, or populated variable files.

## Persistence rules

- SQLite requires one replica and persistent storage mounted at `/app/data`.
- A deployment using PostgreSQL for both stores does not need persistent Bifrost `/app/data` storage. The current Kubernetes Terraform submodules still create a PVC, so account for that resource until conditional PVC creation is implemented.
- Serverless or ephemeral targets require external PostgreSQL for durable configuration and logs.
- Multiple OSS replicas must use the [file-only multinode pattern](/deployment-guides/how-to/multinode); DB-backed configuration changes do not propagate between OSS processes.
- The chart's embedded PostgreSQL and a single cloud database instance are not automatically highly available.
