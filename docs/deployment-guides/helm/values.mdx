This page covers every top-level parameter group in the Bifrost Helm chart's `values.yaml`, how to supply values via `--set` vs `-f`, and where to find ready-made example files.

<Note>
The full values schema is available at [https://getbifrost.ai/schema](https://getbifrost.ai/schema). All `values.yaml` fields map directly to `config.json` fields generated by the chart.
</Note>

## Supplying Values

### One-liner with `--set`

Good for a single field or quick experiments:

```bash
helm install bifrost bifrost/bifrost \
  --set image.tag=v1.4.11 \
  --set replicaCount=3 \
  --set bifrost.client.initialPoolSize=500
```

### Values file with `-f`

Recommended for anything beyond a couple of fields:

```bash
# Create your values file
cat > my-values.yaml <<'EOF'
image:
  tag: "v1.4.11"

replicaCount: 2

bifrost:
  encryptionKey: "your-32-byte-encryption-key-here"
  client:
    initialPoolSize: 500
    enableLogging: true
EOF

# Install
helm install bifrost bifrost/bifrost -f my-values.yaml

# Upgrade later
helm upgrade bifrost bifrost/bifrost -f my-values.yaml

# Upgrade and reuse all previously set values, overriding only one field
helm upgrade bifrost bifrost/bifrost \
  --reuse-values \
  --set replicaCount=5
```

### Multiple values files

Later files override earlier ones - useful for a base + environment-specific overlay:

```bash
helm install bifrost bifrost/bifrost \
  -f base-values.yaml \
  -f production-overrides.yaml
```

## Key Parameters Reference

### Image

| Parameter | Description | Default |
|-----------|-------------|---------|
| `image.repository` | Container image repository | `docker.io/maximhq/bifrost` |
| `image.tag` | **Required.** Image version (e.g. `v1.4.11`) | `""` |
| `image.pullPolicy` | Image pull policy | `IfNotPresent` |
| `imagePullSecrets` | List of pull secret names for private registries | `[]` |

```bash
# Always specify the tag - the chart will not start without it
helm install bifrost bifrost/bifrost --set image.tag=v1.4.11
```

### Replicas & Autoscaling

| Parameter | Description | Default |
|-----------|-------------|---------|
| `replicaCount` | Static replica count (ignored when HPA is enabled) | `1` |
| `autoscaling.enabled` | Enable Horizontal Pod Autoscaler | `false` |
| `autoscaling.minReplicas` | Minimum replicas | `1` |
| `autoscaling.maxReplicas` | Maximum replicas | `10` |
| `autoscaling.targetCPUUtilizationPercentage` | CPU target for scaling | `80` |
| `autoscaling.targetMemoryUtilizationPercentage` | Memory target for scaling | `80` |
| `autoscaling.behavior.scaleDown.stabilizationWindowSeconds` | Cooldown before scale-down (important for SSE streams) | `300` |
| `autoscaling.behavior.scaleDown.policies[0].value` | Max pods removed per period | `1` |

| Parameter | Description | Default |
|-----------|-------------|---------|
| `resources.requests.cpu` | CPU request | `500m` |
| `resources.requests.memory` | Memory request | `512Mi` |
| `resources.limits.cpu` | CPU limit | `2000m` |
| `resources.limits.memory` | Memory limit | `2Gi` |

### Service

| Parameter | Description | Default |
|-----------|-------------|---------|
| `service.type` | `ClusterIP`, `LoadBalancer`, or `NodePort` | `ClusterIP` |
| `service.port` | Service port | `8080` |

### Ingress

| Parameter | Description | Default |
|-----------|-------------|---------|
| `ingress.enabled` | Enable ingress | `false` |
| `ingress.className` | Ingress class (e.g. `nginx`, `traefik`) | `""` |
| `ingress.annotations` | Ingress annotations | `{}` |
| `ingress.hosts` | Host rules | see values.yaml |
| `ingress.tls` | TLS configuration | `[]` |

```yaml
ingress:
  enabled: true
  className: nginx
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
    nginx.ingress.kubernetes.io/proxy-body-size: "100m"
  hosts:
    - host: bifrost.yourdomain.com
      paths:
        - path: /
          pathType: Prefix
  tls:
    - secretName: bifrost-tls
      hosts:
        - bifrost.yourdomain.com
```

### Probes

| Parameter | Description | Default |
|-----------|-------------|---------|
| `livenessProbe.initialDelaySeconds` | Seconds before first liveness check | `30` |
| `livenessProbe.periodSeconds` | Liveness check interval | `30` |
| `readinessProbe.initialDelaySeconds` | Seconds before first readiness check | `10` |
| `readinessProbe.periodSeconds` | Readiness check interval | `10` |

Both probes hit `GET /health`.

### Graceful Shutdown

Bifrost supports long-lived SSE streaming connections. The default `preStop` hook and termination grace period let in-flight streams finish before the pod is killed:

| Parameter | Description | Default |
|-----------|-------------|---------|
| `terminationGracePeriodSeconds` | Total grace period | `60` |
| `lifecycle.preStop.exec.command` | Sleep before SIGTERM so load balancer drains | `["sh", "-c", "sleep 15"]` |

Increase `terminationGracePeriodSeconds` if your typical stream responses take longer than 45 seconds.

### Service Account

| Parameter | Description | Default |
|-----------|-------------|---------|
| `serviceAccount.create` | Create a dedicated service account | `true` |
| `serviceAccount.annotations` | Annotations (e.g. for IRSA, Workload Identity) | `{}` |
| `serviceAccount.name` | Override the generated name | `""` |

### Pod Scheduling

```yaml
# Spread replicas across nodes
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app.kubernetes.io/name: bifrost
        topologyKey: kubernetes.io/hostname

# Pin to specific node pool
nodeSelector:
  node-type: ai-workload

# Tolerate GPU taints
tolerations:
  - key: "gpu"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
```

**Spreading replicas across zones and nodes**

`topologySpreadConstraints` is rendered into the Bifrost pod spec (Deployment or StatefulSet) to spread replicas across nodes or zones, which reduces the chance that losing one takes every replica down. Unlike a required pod anti-affinity rule, it still lets you run more replicas than you have nodes. It does not guarantee a spread: `ScheduleAnyway` only prefers one, and `DoNotSchedule` without `minDomains` can still place every replica in the only eligible domain.

```yaml
topologySpreadConstraints:
  # Hard rule: zone replica counts may differ by at most 1. A pod stays Pending rather than break it.
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
  # Soft rule: prefer spreading across nodes, but never block scheduling.
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
```

| Field | Description |
|-------|-------------|
| `maxSkew` | Maximum difference in Bifrost pods between any two domains (required, at least `1`) |
| `topologyKey` | Node label that defines a domain, e.g. `topology.kubernetes.io/zone` or `kubernetes.io/hostname` (required) |
| `whenUnsatisfiable` | `DoNotSchedule` keeps the pod Pending rather than break the skew; `ScheduleAnyway` only prefers spreading (required) |
| `labelSelector` | Pods counted per domain. Omit it and the chart fills in this release's server pod labels, so only Bifrost's own replicas are counted. An explicit selector, including `{}` (every pod in the namespace), is kept as written |
| `minDomains` | Minimum number of eligible domains. Requires `whenUnsatisfiable: DoNotSchedule`; the chart rejects it with `ScheduleAnyway` |
| `matchLabelKeys`, `nodeAffinityPolicy`, `nodeTaintsPolicy` | Passed through unchanged; see the [Kubernetes docs](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/) |

<Note>
With `DoNotSchedule`, a domain whose nodes are cordoned or tainted still counts toward the skew (the default `nodeTaintsPolicy: Ignore`), so scaling up can leave pods Pending. Use `ScheduleAnyway`, or set `nodeTaintsPolicy: Honor`, when that is not what you want.
</Note>

### Extra Environment Variables

Three ways to inject env vars:

```yaml
# Inline key/value pairs
env:
  - name: HTTP_PROXY
    value: "http://proxy.corp.example.com:3128"

# Map syntax (appended after env)
extraEnv:
  NO_PROXY: "169.254.169.254,10.0.0.0/8"

# Bulk-load from existing Secrets or ConfigMaps
envFrom:
  - secretRef:
      name: my-corp-secrets
  - configMapRef:
      name: my-app-config
```

### Init Containers

```yaml
initContainers:
  - name: wait-for-db
    image: busybox:1.35
    command: ["sh", "-c", "until nc -z postgres-svc 5432; do sleep 2; done"]
```

### Sidecar Containers

Add sidecars the way Kubernetes defines them; the chart has no separate sidecar setting. Every container in the pod shares its network, so a sidecar reaches Bifrost on `localhost:8080`.

**Native sidecars** (Kubernetes 1.29+) are init containers with `restartPolicy: Always`, as described in the [Kubernetes sidecar docs](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/). Add them under `initContainers`. Kubernetes starts a native sidecar before the init containers listed after it and before Bifrost, keeps it running beside Bifrost, restarts it if it exits, and stops it only after Bifrost has shut down. Use one for anything Bifrost needs from startup to shutdown, such as a database proxy. This one runs the Cloud SQL Auth Proxy and points Bifrost's external PostgreSQL at it:

```yaml
initContainers:
  - name: cloud-sql-proxy
    image: gcr.io/cloud-sql-connectors/cloud-sql-proxy:2.14.1
    restartPolicy: Always      # makes this init container a native sidecar
    args:
      - "--port=5432"                       # Postgres listener, on 127.0.0.1 only
      - "--health-check"                    # serve /startup, /liveness and /readiness
      - "--http-address=0.0.0.0"            # health endpoints must be reachable by the kubelet on the pod IP
      - "--http-port=9801"
      - "my-project:us-central1:bifrost-db" # your instance connection name
    startupProbe:              # later init containers and Bifrost wait until the proxy has started
      httpGet:
        path: /startup
        port: 9801
      periodSeconds: 1
      failureThreshold: 30

storage:
  mode: postgres               # store config and logs in PostgreSQL, reached through the proxy

postgresql:
  external:
    enabled: true
    host: "127.0.0.1"          # the proxy, inside the pod
    port: 5432
```

Init containers run in list order, so put a native sidecar before any init container that needs it (for example, a migration step that connects through the proxy). Kubernetes moves on once a native sidecar has started, not once its service is ready: when something depends on the sidecar being ready, give it a `startupProbe`, and Kubernetes waits for the probe to succeed first. The kubelet sends probes to the pod IP, so a sidecar that listens only on `127.0.0.1` (like the proxy's Postgres port) needs a probe on a listener the kubelet can reach, such as the proxy's health endpoint above. On a cluster older than 1.29, the chart refuses to render an init container with `restartPolicy: Always` rather than leave the pod stuck behind an init container that never exits.

**Regular sidecars** go in `extraContainers`, which the chart appends to the pod's containers after Bifrost. They start and stop alongside Bifrost with no ordering guarantee, and work on any Kubernetes version. This one serves Bifrost on a second pod port by forwarding raw TCP:

```yaml
extraContainers:
  - name: port-forwarder
    image: alpine/socat:1.8.0.0
    args: ["TCP-LISTEN:9090,fork,reuseaddr", "TCP:localhost:8080"]
    ports:
      - containerPort: 9090
        name: http-alt
```

A TCP forwarder passes every route on port 8080, the full API included, with the same authentication; it is not a metrics-only endpoint. To expose only `/metrics` on its own port, use an HTTP proxy that allows that path alone.

| Kind | Where to add it | Starts | Stops | Kubernetes |
|------|-----------------|--------|-------|------------|
| Native sidecar | `initContainers`, with `restartPolicy: Always` | Before later init containers and Bifrost | After Bifrost | 1.29+ |
| Regular sidecar | `extraContainers` | With Bifrost | With Bifrost | Any |

Share files between Bifrost and a sidecar by declaring the volume under `volumes`, mounting it into Bifrost with `volumeMounts`, and mounting it into the sidecar in its own `volumeMounts`.

## Helm Operations

### View current values

```bash
helm get values bifrost
```

### Diff before upgrading (requires helm-diff plugin)

```bash
helm diff upgrade bifrost bifrost/bifrost -f my-values.yaml
```

### Rollback

```bash
helm history bifrost
helm rollback bifrost       # to previous revision
helm rollback bifrost 2     # to revision 2
```

### Uninstall

```bash
helm uninstall bifrost

# Also remove PVCs (deletes all data)
kubectl delete pvc -l app.kubernetes.io/instance=bifrost
```

## Advanced Configuration

### Comprehensive Example

A production-ready values file combining the most common settings:

```yaml
# my-values.yaml
image:
  tag: "v1.4.11"

replicaCount: 3

storage:
  mode: postgres

postgresql:
  enabled: true
  auth:
    password: "secure-password"   # use existingSecret in production

autoscaling:
  enabled: true
  minReplicas: 3
  maxReplicas: 10

ingress:
  enabled: true
  className: nginx
  hosts:
    - host: bifrost.example.com
      paths:
        - path: /
          pathType: Prefix

bifrost:
  encryptionKeySecret:
    name: "bifrost-encryption"
    key: "key"
  providers:
    openai:
      keys:
        - name: "primary"
          value: "env.OPENAI_API_KEY"
          weight: 1
  providerSecrets:
    openai:
      existingSecret: "provider-api-keys"
      key: "openai-api-key"
      envVar: "OPENAI_API_KEY"
```

```bash
helm install bifrost bifrost/bifrost -f my-values.yaml
```

Deploy to specific nodes and spread replicas across hosts:

```yaml
nodeSelector:
  node-type: ai-workload

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:

          matchLabels:

  - key: "gpu"
```

Useful for tooling like [Keel](https://keel.sh) for automatic image updates or Datadog APM injection:

<Tab title="Multi-Provider">

Multiple LLM providers with weighted load balancing.

```bash
kubectl create secret generic provider-keys \
  --from-literal=openai-api-key='sk-...' \
  --from-literal=anthropic-api-key='sk-ant-...' \
  --from-literal=gemini-api-key='your-gemini-key'
```

```yaml
  tag: "v1.4.11"

    enableLogging: true

          value: "env.OPENAI_API_KEY"
          weight: 2    # 50% of traffic

      keys:
        - name: "anthropic-primary"
          value: "env.ANTHROPIC_API_KEY"
          weight: 1    # 25%

      keys:

      existingSecret: "provider-keys"
```
