This guide deploys Bifrost to an existing AKS cluster using the Helm chart. It covers the Bifrost image, secrets, storage, database connection, service exposure, verification, and scaling.

<Note>
The Helm configuration is validated in the repository. The complete guide is not continuously exercised in a live Azure subscription, so test the selected values in a non-production cluster before rollout.
</Note>

## One-click deploy

<a className="deploy-btn" href="https://shell.azure.com" target="_blank" rel="noopener noreferrer"><AzureMark />Deploy on Azure</a>

If you do not have an AKS cluster, the one-click path runs Bifrost on Azure Container Instances instead. The button opens Azure Cloud Shell, already signed in as you. Paste one line into it:

```bash
( git -C bifrost pull --ff-only 2>/dev/null || git clone --depth 1 https://github.com/maximhq/bifrost ) && bifrost/deploy/azure/deploy.sh
```

The script uses your current subscription, registers the Container Instances, PostgreSQL, Key Vault, Managed Identity, and Network resource providers, and applies [`terraform/examples/azure-aci-postgres`](https://github.com/maximhq/bifrost/tree/main/terraform/examples/azure-aci-postgres) with the Terraform that Cloud Shell ships:

| Resource | What it is |
|---|---|
| Resource group, VNet, subnet, network security group | Network scaffold. The container group runs on a public IP outside the subnet, so the NSG does not restrict who reaches it |
| Key Vault and user-assigned identity | Holds `config.json`; identity for the container group |
| Azure Database for PostgreSQL Flexible Server 16 (`B_Standard_B1ms`, 32 GB, 7-day backups, TLS required) | Configuration store and log store |
| Container group, 1 core and 2 GB, public IP with a DNS label | The Bifrost image on `http://<prefix>.<region>.azurecontainer.io:8080` |

The database has a public endpoint that enforces TLS and, through Azure's "allow Azure services" firewall rule, admits connections from any Azure-hosted address, not only this deployment; that is how the container group, which has no fixed egress address, reaches it. The generated credentials are the access control. The AKS path below uses the same database module and therefore the same access scope; a private endpoint would need a VNet-integrated Flexible Server, which these examples do not provision. The generated `BIFROST_ENCRYPTION_KEY` and `BIFROST_SETUP_TOKEN` travel as secure environment variables; the script prints the token. Apply takes about ten minutes, most of it the Flexible Server.

**Before you open the dashboard:** Container Instances serve plain HTTP on a public IP that cannot be restricted by source address, so the setup token, the admin password and every provider key you paste would travel unencrypted. Put Azure Front Door, Application Gateway, or your own proxy with TLS in front before you enter any credential, and use the HTTPS address from then on. That frontend adds TLS but does not stop clients from reaching the container's public IP directly, so this path has no private origin; when the origin itself must be unreachable from the internet, use the AKS deployment below with a private ingress. Move to AKS as well once you need ingress, scaling, or Enterprise clustering.

Then open the URL, [create the first admin account](/quickstart/gateway/setting-up-auth) with the token, add a provider key, and [create a virtual key](/features/governance/virtual-keys); inference routes require one because the endpoint is public.

Terraform state stays in the example directory inside Cloud Shell's persistent home, so choose persistent storage when Cloud Shell first asks (an ephemeral session loses the state while the Azure resources remain), or configure a remote backend before running the script. The state file holds the database password, the encryption key and the setup token: restrict access to that storage account or backend, and never commit or share the file. Keep the clone to change or destroy the stack.

Environment overrides for the first run: `AZURE_LOCATION`, `AZURE_SUBSCRIPTION_ID`, `BIFROST_NAME_PREFIX` (also the DNS label), `BIFROST_IMAGE_TAG` (pin a release), `BIFROST_IMAGE_REPOSITORY`, and `BIFROST_AUTO_APPROVE=1`. They seed `terraform.tfvars`; the script keeps that file on reruns, so later changes such as a new image tag go into `terraform.tfvars` followed by `terraform apply`. Do not change `region` on an existing deployment that way: the database cannot move, so Terraform would replace it and the plan would destroy both stores; a region move is a new stack plus a database migration. Tear down with `terraform destroy` in the example directory.

**Enterprise:** the script applies before you could add anything, so put the credential in place first: create `terraform/examples/azure-aci-postgres/terraform.tfvars` in the clone with `region`, `name_prefix`, `image_repository` (the registry path issued for your organization), `image_tag`, and `registry_server`, `registry_username`, `registry_password`, then run the script; it keeps an existing `terraform.tfvars` and uses those values. The three `registry_*` values become an `image_registry_credential` on the container group, which is required because Container Instances cannot pull a private image with a managed identity alone. Alternatively deploy the public image first and change all four values in `terraform.tfvars` before a second `terraform apply`. The [enterprise Azure guide](/deployment-guides/enterprise/azure) covers AKS workload identity, which Container Instances cannot use; the static credential this path needs is the Docker login from the [on-premise guide](/deployment-guides/enterprise/on-premise#docker-deployment): `registry_server` is the Artifact Registry host (`REGION-docker.pkg.dev`), `registry_username` is `_json_key`, and `registry_password` is the contents of the issued key file. Obtain that key before the first apply.

### Create an AKS cluster instead

For a Kubernetes deployment without an existing cluster, run the AKS script in the same Cloud Shell:

```bash
( git -C bifrost pull --ff-only 2>/dev/null || git clone --depth 1 https://github.com/maximhq/bifrost ) && bifrost/deploy/aks/deploy.sh
```

It applies [`terraform/examples/azure-aks-postgres`](https://github.com/maximhq/bifrost/tree/main/terraform/examples/azure-aks-postgres) in two phases: the AKS cluster first (about ten minutes), then, after `az aks get-credentials` has written the kubeconfig, the same Flexible Server, Kubernetes Secrets `<name_prefix>-config` and `<name_prefix>-runtime` (`bifrost-config` and `bifrost-runtime` with the default prefix), and one Bifrost pod behind a public `LoadBalancer` Service whose URL the script prints. The environment overrides and the setup-token flow are the same as above; the Enterprise image is attached through the cluster identity as described below, not through a registry credential.

**Before you open the dashboard:** the `LoadBalancer` Service is plain HTTP, so the setup token, the admin password and every provider key you paste would travel unencrypted. Put Application Gateway ingress or an ingress controller with TLS in front before you enter any credential. Narrowing `allowed_cidr` in `terraform.tfvars` to your own address and applying again (it becomes the Service's `loadBalancerSourceRanges` and the subnet NSG rule for port 80) limits who can connect and is worth doing as well, but it encrypts nothing, so it is not a substitute for TLS. Once TLS is in front, set `service_type = "ClusterIP"` in `terraform.tfvars` and apply so the port-80 load balancer disappears, and use the HTTPS URL from then on. Do both before inviting other users; then create the first admin account with the printed setup token, add a provider key, and create a virtual key.

Terraform state stays in the example directory inside Cloud Shell's persistent home; as above, choose persistent storage or a remote backend first, and protect the state file, which holds the database password, the encryption key and the setup token. Keep the clone to change or destroy the stack.

Environment overrides for the first run: `AZURE_LOCATION`, `AZURE_SUBSCRIPTION_ID`, `BIFROST_NAME_PREFIX`, `BIFROST_IMAGE_TAG` (pin a release), `BIFROST_IMAGE_REPOSITORY`, and `BIFROST_AUTO_APPROVE=1`. They seed `terraform.tfvars`; later changes such as a new image tag go into that file followed by `terraform apply`. Do not change `region` on an existing deployment that way: the database cannot move, so Terraform would replace it and the plan would destroy both stores; a region move is a new stack plus a database migration. Tear down with `terraform destroy` in the example directory.

**Enterprise:** the Terraform Deployment pulls with the cluster's kubelet identity, not a pull secret, and that identity exists only once the script has created the cluster. So run the script first with `BIFROST_IMAGE_REPOSITORY` unset, which deploys the public image. Then import the Enterprise image into an Azure Container Registry in your subscription using the issued key file from the [on-premise guide](/deployment-guides/enterprise/on-premise#docker-deployment) as the source credential (`az acr import --name <registry> --source REGION-docker.pkg.dev/<project>/<repository>/<image>:<tag> --username _json_key --password "$(cat bifrost-credentials.json)" --image bifrost-enterprise:<tag>`), attach it with `az aks update --resource-group "$(terraform output -raw cluster_resource_group)" --name "$(terraform output -raw cluster_name)" --attach-acr <registry>` from the example directory (the outputs hold the real names, also when `resource_group_name` points at an existing group), set `image_repository` in `terraform.tfvars` to that registry path and run `terraform apply`. Starting with the private path would leave the pod in `ImagePullBackOff`. The [enterprise Azure guide](/deployment-guides/enterprise/azure) covers workload identity for pods that pull straight from Artifact Registry, which this import path does not use.

## Bifrost on AKS

| Bifrost setting | AKS configuration |
|---|---|
| Container | OSS or supplied Enterprise image on `linux/amd64` or `linux/arm64` Linux nodes |
| HTTP and health | `ClusterIP` Service on `8080/TCP`; `GET /health` |
| SQLite (OSS only) | One replica and a `ReadWriteOnce` managed disk or another compatible CSI volume |
| PostgreSQL | PostgreSQL 16 or later reachable from the cluster, inside or outside Azure |
| External access | Gateway API, ingress, Service `LoadBalancer`, service mesh, Application Gateway, or external proxy |
| Enterprise mesh | Kubernetes discovery plus bidirectional `10101/TCP+UDP` and `10102/TCP` |
| Image pull | Public Docker Hub for OSS; customer Enterprise registry federation/pull secret from [Enterprise Azure](/deployment-guides/enterprise/azure) |

Bifrost Enterprise requires PostgreSQL 16 or later for both stores and does not support SQLite. The SQLite path below is available only for OSS deployments.

## Deploy Bifrost

The commands below use an existing AKS cluster and PostgreSQL database. Run them from Bash after replacing every value inside angle brackets.

### Step 1: Connect to AKS

```bash
export AZURE_RESOURCE_GROUP='<AZURE_RESOURCE_GROUP>'
export AKS_CLUSTER='<AKS_CLUSTER_NAME>'
export BIFROST_VERSION='<BIFROST_VERSION>'
az aks get-credentials \
  --resource-group "${AZURE_RESOURCE_GROUP}" \
  --name "${AKS_CLUSTER}"

kubectl get nodes
helm version
```

Continue only after the nodes report `Ready`.

### Step 2: Create secrets and Helm values

The encryption key protects persisted credentials. Create it once, keep it unchanged after Bifrost writes encrypted data, and use the same value for every replica. Replacing the key makes existing encrypted values unreadable.

```bash
kubectl create namespace bifrost \
  --dry-run=client -o yaml | kubectl apply -f -

read -r -s -p 'Stable Bifrost encryption key: ' BIFROST_ENCRYPTION_KEY; echo
kubectl create secret generic bifrost-encryption \
  --namespace bifrost \
  --from-literal=encryption-key="${BIFROST_ENCRYPTION_KEY}" \
  --dry-run=client -o yaml | kubectl apply -f -
unset BIFROST_ENCRYPTION_KEY
```

Choose the storage configuration for this deployment:

<Tabs>
<Tab title="PostgreSQL">

```bash
export POSTGRES_HOST='<POSTGRES_HOST>'
export POSTGRES_PORT='5432'
export POSTGRES_USER='<POSTGRES_USER>'
export POSTGRES_DATABASE='<POSTGRES_DATABASE>'

read -r -s -p 'PostgreSQL password: ' POSTGRES_PASSWORD; echo
kubectl create secret generic postgres-credentials \
  --namespace bifrost \
  --from-literal=password="${POSTGRES_PASSWORD}" \
  --dry-run=client -o yaml | kubectl apply -f -
unset POSTGRES_PASSWORD

cat > bifrost-values.yaml <<EOF
image:
  repository: docker.io/maximhq/bifrost
  tag: "${BIFROST_VERSION}"

replicaCount: 1

storage:
  mode: postgres

postgresql:
  enabled: false
  external:
    enabled: true
    host: "${POSTGRES_HOST}"
    port: ${POSTGRES_PORT}
    user: "${POSTGRES_USER}"
    database: "${POSTGRES_DATABASE}"
    sslMode: require
    existingSecret: postgres-credentials
    passwordKey: password

bifrost:
  encryptionKeySecret:
    name: bifrost-encryption
    key: encryption-key
EOF
```

This uses PostgreSQL for both Bifrost stores and does not create a Bifrost SQLite PVC. Enterprise customers should replace the image settings and registry authentication using the values supplied by Maxim.


Azure Database for PostgreSQL is one Azure-hosted option. The database may instead be operated by the customer or another provider as long as the cluster can reach it.

Verify connectivity from the cluster before installing Bifrost:

```bash
kubectl run postgres-check --namespace bifrost \
  --image=postgres:16-alpine --restart=Never \
  --env="PGHOST=${POSTGRES_HOST}" --env="PGPORT=${POSTGRES_PORT}" \
  --env="PGDATABASE=${POSTGRES_DATABASE}" --env="PGUSER=${POSTGRES_USER}" \
  --env="PGSSLMODE=require" \
  --command -- sleep 3600

kubectl wait --namespace bifrost --for=condition=Ready pod/postgres-check --timeout=2m
kubectl exec --namespace bifrost -it postgres-check -- psql \
  -c "SHOW server_version;" \
  -c "SHOW server_encoding;"
kubectl delete pod --namespace bifrost postgres-check
```

Enter the PostgreSQL password when psql prompts. A successful connection confirms DNS, TCP, TLS, and database authentication from the pod network. Confirm that `server_version` reports PostgreSQL 16 or later and `server_encoding` reports `UTF8`.

</Tab>
<Tab title="SQLite (OSS only)">

This option is available only for OSS Bifrost. Use SQLite for a single replica and select a compatible ReadWriteOnce StorageClass such as an approved managed-disk CSI class.

```bash
kubectl get storageclass

cat > bifrost-values.yaml <<EOF
image:
  repository: docker.io/maximhq/bifrost
  tag: "${BIFROST_VERSION}"

replicaCount: 1

storage:
  mode: sqlite
  persistence:
    enabled: true
    accessMode: ReadWriteOnce
    size: 10Gi
    storageClass: "<STORAGE_CLASS>"

bifrost:
  encryptionKeySecret:
    name: bifrost-encryption
    key: encryption-key
EOF
```

Replace `<STORAGE_CLASS>` with a class returned by `kubectl get storageclass`. This creates persistent `/app/data` storage for the OSS SQLite deployment. PostgreSQL is not required for this OSS option.

</Tab>
</Tabs>

### Step 3: Install Bifrost

```bash
helm repo add bifrost https://maximhq.github.io/bifrost/helm-charts
helm repo update

helm upgrade --install bifrost bifrost/bifrost \
  --namespace bifrost \
  --values bifrost-values.yaml \
  --atomic \
  --timeout 15m
```

### Step 4: Verify and access Bifrost

```bash
kubectl wait --namespace bifrost \
  --for=condition=Ready pod \
  --selector=app.kubernetes.io/name=bifrost \
  --timeout=10m

kubectl get pods,service --namespace bifrost
```

Choose how you want to access the deployment:

<Tabs>
<Tab title="Without a load balancer">

```bash
kubectl port-forward service/bifrost --namespace bifrost 8080:8080
```

Keep that terminal open. In another terminal:

```bash
curl --fail --show-error http://127.0.0.1:8080/health
```

</Tab>
<Tab title="With a load balancer">

```bash
cat >> bifrost-values.yaml <<'EOF'

service:
  type: LoadBalancer
EOF

helm upgrade bifrost bifrost/bifrost \
  --namespace bifrost \
  --values bifrost-values.yaml \
  --atomic \
  --timeout 15m

kubectl get service bifrost --namespace bifrost --watch
```

After `EXTERNAL-IP` displays an address, stop the watch and run:

```bash
export BIFROST_HOST="$(kubectl get service bifrost \
  --namespace bifrost \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}{.status.loadBalancer.ingress[0].ip}')"

curl --fail --show-error "http://${BIFROST_HOST}:8080/health"
```

This creates an HTTP endpoint. Configure TLS through the selected Azure or Kubernetes frontend before exposing Bifrost to untrusted clients.

<Note>
AKS-managed Azure Load Balancers use a 30-minute TCP idle timeout by default. For streams that might remain idle longer, configure TCP keepalive or adjust the load balancer idle timeout.
</Note>

</Tab>
<Tab title="With ingress">

This example uses the [AKS application-routing add-on](https://learn.microsoft.com/en-us/azure/aks/app-routing). Enable the add-on before applying these values.

```bash
cat > ingress-values.yaml <<'EOF'
service:
  type: ClusterIP

ingress:
  enabled: true
  className: webapprouting.kubernetes.azure.com
  annotations:
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
    nginx.ingress.kubernetes.io/proxy-request-buffering: "off"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
  hosts:
    - host: "<BIFROST_HOSTNAME>"
      paths:
        - path: /
          pathType: Prefix
EOF

helm upgrade bifrost bifrost/bifrost \
  --namespace bifrost \
  --values bifrost-values.yaml \
  --values ingress-values.yaml \
  --atomic \
  --timeout 15m

kubectl get ingress --namespace bifrost --watch
```

Point the hostname to the ingress address, configure TLS through the application-routing add-on or another certificate integration, and verify `https://<BIFROST_HOSTNAME>/health`.

</Tab>

## Scale Bifrost

- OSS with SQLite: one replica.
- OSS with database-managed configuration: one replica, or use [file-only OSS multinode](/deployment-guides/how-to/multinode).
- Enterprise: PostgreSQL plus [Cluster Mode and HA](/deployment-guides/helm/cluster), pod-discovery RBAC, and internal mesh ports.

Azure load balancing distributes requests but does not synchronize Bifrost state.

## Upgrade, troubleshooting, and production

Follow the [upgrade guidance](/deployment-guides/runtime-contract#upgrade-bifrost). Diagnose with:

```bash
kubectl describe pod --namespace bifrost -l app.kubernetes.io/name=bifrost
kubectl get events --namespace bifrost --sort-by=.lastTimestamp
kubectl describe pvc --namespace bifrost
kubectl logs --namespace bifrost -l app.kubernetes.io/name=bifrost --tail=200
```

- Pending OSS SQLite pod: inspect the PVC, CSI driver, StorageClass, and zone/node-pool constraints.
- `ImagePullBackOff`: verify the image repository/tag and Enterprise registry token refresh.
- `/health` `503`: verify configured stores from the pod network and inspect startup logs.
- Fixed streaming cutoff: inspect all ingress, gateway, and Azure frontend timeouts/buffering.
- Missing Enterprise nodes: check pod-discovery RBAC and bidirectional cluster ports.

Complete the [deployment verification checklist](/deployment-guides/runtime-contract#verify-the-deployment) for database availability, backups, TLS, secrets, autoscaling, and monitoring. See [Enterprise clustering](/enterprise/clustering) when the deployment spans several clusters or regions.
