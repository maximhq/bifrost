Heroku runs Bifrost on the container stack with Heroku Postgres attached. The one-click button reads `app.json` and `heroku.yml` from the root of the Bifrost repository.

<Note>
**Support level: Preview.** This guide is not continuously exercised against a live Heroku account.
</Note>

## One-click deploy

<a className="deploy-btn" href="https://heroku.com/deploy?template=https://github.com/maximhq/bifrost" target="_blank" rel="noopener noreferrer"><HerokuMark />Deploy to Heroku</a>

The button creates:

| Resource | What it is |
|---|---|
| Container-stack app | Built from [`deploy/heroku/Dockerfile`](https://github.com/maximhq/bifrost/blob/main/deploy/heroku/Dockerfile), a one-line `FROM maximhq/bifrost:<pinned tag>`, so the "build" is a pull of the published release |
| `heroku-postgresql:essential-0` | Attached as `DATABASE_URL` |
| `BIFROST_ENCRYPTION_KEY`, `BIFROST_SETUP_TOKEN` | Generated by Heroku at creation (`generator: secret`) |

Heroku builds images with the build context fixed to the Dockerfile's directory, which is why the repository Dockerfile cannot be used there and the one-liner exists instead. The app receives `config.json` through `BIFROST_CONFIG_JSON`; the entrypoint derives `PG_*` from `DATABASE_URL` and listens on Heroku's `PORT`. Inference routes require a virtual key.

After the deploy finishes:

1. Read the setup token: `heroku config:get BIFROST_SETUP_TOKEN -a <app>`, or open the app's Settings and reveal config vars.
2. Open the app URL and [create the first admin account](/quickstart/gateway/setting-up-auth) with it.
3. Add a provider key and [create a virtual key](/features/governance/virtual-keys).

The release pipeline moves the pinned tag in `deploy/heroku/Dockerfile` on every stable release; redeploy the app to pick it up.

**Enterprise:** Heroku cannot build from a private `FROM` line, so the button and `heroku.yml` only work for the public image. Deploy the Enterprise image through the Heroku Container Registry instead: create the app on the container stack with the Postgres add-on (`heroku create <app> --stack container`, `heroku addons:create heroku-postgresql:essential-0 --app <app>`; `app.json`'s `stack` only applies to the button path), set `BIFROST_CONFIG_JSON`, `BIFROST_ENCRYPTION_KEY` and `BIFROST_SETUP_TOKEN` as config vars, pull the image with the credential issued for your organization for `linux/amd64` (`docker pull --platform linux/amd64 <image>`; Heroku runs x86-64 images only), tag it `registry.heroku.com/<app>/web`, run `heroku container:login` and `docker push registry.heroku.com/<app>/web`, then `heroku container:release web --app <app>`. Enterprise requires PostgreSQL for both stores, which the add-on provides.

## Platform requirements

| Setting | Value |
|---|---|
| Container port | Heroku's `PORT`, honoured by the entrypoint |
| Health | Heroku has no HTTP health check; use `GET /health` from your monitoring |
| Storage | PostgreSQL for both stores; dyno filesystems are ephemeral |
| Dynos | One `web` dyno. OSS replicas do not share live configuration |
| User | Heroku runs containers as a non-root user; the image's group-writable `/app/data` supports that |

See [Bifrost Deployment Requirements](/deployment-guides/runtime-contract) for the shared container values.

## Troubleshooting

- `R10 Boot timeout`: the dyno did not bind to `PORT` in time, usually because database migrations against a cold `essential-0` database took long. Restart the dyno once the add-on is ready.
- SSL errors against Heroku Postgres: the derived `PG_SSL_MODE` is `prefer`, which negotiates TLS. Set `PG_SSL_MODE=require` as a config var to force it.
- Build fails pulling the image: Heroku needs Docker Hub access during the build; retry, or pin a different tag in a fork. A private image cannot be used in the `FROM` line at all; see the Enterprise note above.
