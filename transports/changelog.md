## ✨ Features

- **Agent Gateway (A2A)** - Bifrost now proxies A2A agents. Register an upstream agent by its agent card URL (`POST /api/agents`, `POST /api/agents/inspect`, or the new top-level `agents` array in config.json, reconciled by name at startup) and clients reach it at `/agents/a2a/<name>/.well-known/agent-card.json`, `/agents/a2a/<name>/json-rpc` (JSON-RPC and SSE streaming) and `/agents/a2a/<name>/rest/...`, plus an optional shared gRPC listener routed by `<agent>.<a2a_grpc_base_domain>:<a2a_grpc_port>`. The runtime caches cards and clients, refreshes a stale interface on 404/405/410/426, supports header, OAuth and TLS upstream auth, runs A2A plugin hooks, and delivers push notifications through a durable, retried outbox (`/agents/a2a/<name>/push/callback`, authenticated with a per-config token). Push callbacks to loopback or private addresses stay blocked unless the new `server.a2a_allow_private_push_callbacks` is on (default off). Access is governed per virtual key with `agent_grants` (omit to keep, `[]` to clear, unknown agents rejected atomically) and `allow_by_default` per agent; ungranted or disabled agents return `403`. Every A2A operation and stream event gets its own log row (relational, ClickHouse, or hybrid with object-store payloads) in a new Agent Logs workspace with session grouping, raw capture and DAC-bounded filters, LLM and MCP logs carry the A2A correlation id, and A2A client spans plus the `a2a.client.operation.duration` metric reach connectors. The dashboard adds an agent sheet with auth fields and a card preview, push-config UI and an Agent Gateway settings page; Helm adds `bifrost.agents[]`, `bifrost.client.a2aExternalClientUrl`, `bifrost.server.a2aGrpcBaseDomain` and `bifrost.server.a2aGrpcPort`
- **Warp AI Assistant (alpha)** - Warp (formerly Odin) is a new in-dashboard agent that answers questions about the deployment's logs, spend, latency and governance in plain language, using read-only tools (`query_logs`, `count_logs`, `get_log_detail`, `get_request_trace`, `query_metrics`, `query_usage_by`, `query_model_performance`, `render_chart`, `describe_filter_space`, `describe_virtual_key`, `describe_user_limits`, `ask_user`). It asks multiple-choice clarifying questions, draws inline charts, links to matching rows on the Logs page, resolves "today", "yesterday" and bare dates in the asker's time zone, and filters by agent name and `x-bf-agent-correlation-id`. Admins set a default model plus up to 20 more models users can switch between, `temperature`, `reasoning_effort` and max iterations (2 to 20) at `/api/warp/config`; chat streams from `/api/warp/chat` with history under `/api/warp/conversations` (100-conversation cap). Warp calls the gateway in-process, its calls are logged and governed under the app name **Warp**, signed-in users without an access profile are served, and it only reads rows the asker may see. Governance refusals return their own error codes (`access_denied`, `budget_exceeded`, `rate_limited`, `model_blocked`), and the chat panel is a resizable dock. Gated by the `warp` feature flag, on by default in OSS and off by default in Enterprise
- **Warp Semantic Log Search** - Completed LLM logs can be embedded into a vector store so Warp's `semantic_search_logs` finds conversations by meaning. The embedding provider, model, dimension and namespace are set in Warp settings; new logs are indexed live, and older logs by a resumable, concurrent background backfill (`/api/warp/log-index/backfill`, `/backfill/status`, `/backfill/cancel`, `/api/warp/log-index/status`). Restricted callers get results prefiltered to rows they can see, the similarity threshold is one 0 to 1 scale on every vector store (default 0.5, Weaviate included), and a finished backfill is hidden once the embedding space changes
- **GPT Live Sessions** - Bifrost now proxies OpenAI GPT Live sessions over WebSocket and WebRTC at `/v1/live/sessions`, with a sideband `/v1/live/sessions/{session_id}/attach` WebSocket and recording downloads at `/v1/live/sessions/{session_id}/content` (logged as `live_content`). Voice time is billed in 30-second windows from `input_cost_per_second` on a `live` pricing row and backend Responses calls are billed per turn, with governance checked at each window and one session log row carrying transcript, delegations and costs. Live has its own `live` allowed request type (`realtime` does not imply it). Sessions are bound to the virtual key that opened them, keys are picked only from those governance allows, later billing units on an excluded key return `403`, and sideband attachments run through the plugin pipeline as `live_sideband` with their own log row. Failed backend delegations are recorded on the delegation instead of failing the session, an upstream that ends without `session.closed` gives the client `502 server_error`, a failed WebRTC setup still records the 15-second minimum, `x-bf-direct-key` works on WebSocket upgrades, and `?provider=` or `x-model-provider` picks the provider on attach and content routes
- **Cloudflare Workers AI Provider** - New first-party `cloudflare` provider for chat completions (streaming included), Responses, embeddings and model listing against Workers AI. Every key needs `cloudflare_key_config.account_id` (supports `env.` references); the base URL defaults to `https://api.cloudflare.com/client/v4`. Clef decision models (`clef`, `clef-flash`) are served natively on `/v1/decisions` with image input, and the Cloudflare `{result, success, errors}` envelope is unwrapped. A migration dialog in the UI moves an existing custom provider named `cloudflare` onto the new provider
- **Provider-Injected MCP Tools** - A provider can carry `injected_tools`, a list of `{name, mcp_client_name, tool_name}` entries. Bifrost adds each MCP tool to every chat and Responses request for that provider (past client and request tool filters), runs it server side when the model calls it (non-streaming, streaming chat, streaming Responses and the Anthropic passthrough path), and returns only the final answer with usage summed across turns. An entry named `web_search` replaces any native web search the client sends; any other name replaces a client tool of the same name. Configure it in the provider's new Tools tab, the provider API or config.json. Depth is capped by `mcp_agent_depth`
- **OAuth-Minted Keys for OpenAI-Compatible Providers** - Keys on `openai` and on custom providers with an `openai` base can set `oauth_key_config` instead of a static `value`. Bifrost mints a bearer from the token endpoint with the `client_credentials` grant (HTTP Basic or `auth_style: "body"`) or the `jwt_bearer` grant (RFC 7523, RSA/EC signed assertions), caches it per credential, refreshes it a minute before expiry and backs off on rejected credentials. A non-empty `value` always wins. Available in the API, config.json, Helm and a new "OAuth (minted token)" tab in the key form. Databricks OAuth M2M and GitHub Copilot now mint through the same shared token cache, so a rejected Databricks service principal is backed off instead of hitting the token endpoint on every request
- **Decisions API in OpenAI Shape** - `POST /v1/decisions` now takes `input` (text, messages with image parts, or structured data) and an ordered `questions` list, each with `type` (`predicate`, `choice`, `score`), optional `name`, `instructions`, `criteria`, `choices` or `levels`, plus `safety_identifier`. Answers come back as a list in question order, with Laya answer fields, response `routing` and state/truncation usage fields passed through. New `/openai/v1/decisions` and `/openai/decisions` routes (also under `/langchain`, `/litellm`, `/pydanticai`) accept the OpenAI SDK's native request; an OpenAI-based provider's body is relayed unchanged and others are rebuilt into OpenAI's response shape
- **Native Decision Models on More Providers** - `/v1/decisions` now reaches native decision endpoints on OpenAI (`gpt-6-luna`), Perplexity (`pplx-decider-*`), Ollama (local System One models `nimble`, `tev1`, `clef`, `clef-flash`, `laya` on `/v1/systemone`, with `keep_alive` and base64 images) and OpenRouter (TypeSafe Jev models and any model the datasheet marks `supports_decisions`, listed live with response headers forwarded). These providers returned `unsupported_operation` before (thanks [@hcavarsan](https://github.com/hcavarsan)!)
- **Decision Emulation Is Opt-In** - Decision requests to a model with no native decisions endpoint are no longer emulated through the model's Responses API by default. They return `unsupported_operation` with a message naming the model and `convert_decision_to_responses`. Enable emulation with the new compat setting `convert_decision_to_responses` (UI: Compatibility, "Emulate Decisions API on non-decision models") or per request with `x-bf-compat: ["convert_decision_to_responses"]`
- **TypeSafe as a Custom Provider Base** - Custom providers can use `base_provider_type: "typesafe"`, so a second TypeSafe-compatible endpoint (for example self-hosted Laya or Nimble) runs with its own keys, name, `allowed_requests` and `request_path_overrides` for `decisions` and `list_models`, with keyless listing. The dashboard offers TypeSafe as a base format and adds a Decisions toggle to allowed requests
- **Decision Pricing Rates** - New datasheet and override fields `input_cost_per_token_decisions` and `output_cost_per_token_decisions` price decisions served natively by chat-row models such as `gpt-6-luna`; rows without them fall back to the normal token rates. Decision requests on variable-price models no longer bill a negative cost
- **Complexity Router Decision-Model Classifier** - The complexity router can now classify with a decision model (TypeSafe Jev by default; Laya, Nimble, Clef and OpenAI decision models such as `gpt-6-luna` also work), as the primary classifier or as the semantic classifier's fallback. Only user turns are sent (`previous_message_count`, `timeout`), per-tier guidance (definition, signals, examples) can be edited with shipped defaults returned as `jev_defaults` on the status endpoint, and decision calls are billed under the routing cost with a `RequestType`. `GET /api/models?decisions=true` lists only models that serve decisions natively, `decisions` is a request type in pricing overrides and routing CEL rules, decision logs show their questions, and the LLM fallback classifier no longer sends `temperature: 0`. The dashboard has a stepped classifier setup and settings sheets
- **Durable Queue Framework** - New `framework/queue` package: a durable queue with consumer groups, at-least-once delivery, per-key ordering, retries, dead-lettering and lease heartbeats. Backends: in-memory, and a `logstore` type that keeps queue tables in the logs database on SQLite (single process), Postgres (multi-instance, `SKIP LOCKED` claims, `LISTEN/NOTIFY` wakeups) and ClickHouse. Available to framework consumers; the gateway does not use it yet
- **Multimodal Embeddings** - `/v1/embeddings` input now accepts content parts (`text`, `image`, `audio`, `video`, `file`, `tokens`) and per-item `params` overrides, served by Cohere, Gemini (including `:batchEmbedContents`) and Vertex (including `gs://` URIs, `multimodalembedding@001` video segments and `embedContentConfig.documentOcr`/`audioTrackExtraction`). Bedrock gains Nova multimodal (`amazon.nova-2-multimodal-embeddings-v1:0`) and Titan multimodal (`amazon.titan-embed-image-v1`) embeddings, `encoding_format` maps to Cohere `embedding_types`, and Parasail serves embeddings. OpenAI-compatible providers get only `encoding_format` and `dimensions` (Mistral no longer returns `422` on `task_type`), and the semantic cache hashes `task_type`, `title` and `auto_truncate`. Embedding inputs are stored in a new `embedding_input` log column and shown in the log view
- **Shell, apply_patch and Programmatic Tool Callers** - The Responses API now supports OpenAI's `shell` tool with `shell_call`/`shell_call_output` items (streaming included) and the `apply_patch` tool with `apply_patch_call`/`apply_patch_call_output` items and diff stream events. `allowed_callers` is translated between OpenAI's `programmatic` and Anthropic's versioned `code_execution_*` callers on chat and Responses. Gemini `executableCode`/`codeExecutionResult` parts map to `code_interpreter_call` items, and `code_interpreter` reaches Gemini as `codeExecution`. Shell, code interpreter, image generation and computer tools are dropped for Bedrock and Bedrock Mantle, and the semantic cache treats `shell_call` and `apply_patch_call` as tool calls
- **Retrieve a Single Model** - New `GET /v1/models/{model}` returns one model's metadata, implemented for OpenAI, Anthropic (with alias resolution), Cohere, Gemini, Mistral and Ollama, with `shutdown_date` where the provider announces one. Gated by the `model_retrieve` allowed request and exempt from budgets and rate limits
- **xAI Realtime** - xAI is now a realtime voice provider on the WebSocket gateway, including client-secret minting through `/v1/realtime/client_secrets`. Browser clients can authenticate with the `xai-client-secret.<token>` subprotocol as well as `openai-insecure-api-key.<token>`; an empty, whitespace-containing or conflicting subprotocol credential returns `400` before the upgrade, and mint requests that carry session settings are rejected (send them with `session.update`). Responses streaming keeps the provider stop reason from the newest chunk that has one, and the logging plugin marks `refusal`, `content_filter` and `safety` stops as errors of type `model_refusal`
- **Bedrock Passthrough** - New `/bedrock_passthrough` route forwards the three Bedrock operations Bifrost has no native route for: InvokeAgent (streamed as AWS sends it), knowledge-base Retrieve, and ApplyGuardrail. Any other path, method or malformed identifier returns `400`. InvokeAgent and Retrieve are SigV4-signed with the key's AWS credentials (an API-key-only key is refused with `400`), and AWS status, body and `X-Amzn-*` headers come back unchanged. Azure `prompt_filter_results` and per-choice `content_filter_results` are now passed through on chat responses
- **Vertex AI Workload Identity Federation from AWS** - Vertex keys can set `vertex_key_config.aws_workload_identity` (`audience`, `service_account_email`, `token_lifetime_seconds`, `aws_region`, `aws_role_arn`) to authenticate from EKS IRSA, Pod Identity, ECS task roles or EC2 instance profiles with no stored GCP or AWS key. gcloud-generated AWS `external_account` JSON now also resolves AWS credentials through the AWS SDK chain. New "Workload Identity (AWS)" tab in the key form
- **Web Search Priced per Request** - Provider-hosted web search is now reported as `usage.tool_usage.web_search.num_requests` (top-level `tool_usage` on Responses) for Anthropic, Gemini, Perplexity and OpenAI Responses, and billed with the new pricing field `web_search_cost_per_request`. Existing values are copied over by migration, and datasheet rows still carrying `search_context_cost_per_query` are read as the new field
- **Ignore Provider-Reported Cost** - New per-provider `ignore_provider_cost` setting (UI: provider Pricing tab, default `false`) discards the `usage.cost` a provider reports, for providers such as Cortecs that report credits, and prices requests from the model catalog and pricing overrides for logs, budgets, telemetry and streamed totals. The client response keeps the provider's figure
- **Compat: Route Reasoning-Only Models to Responses** - New compat setting `force_reasoning_only_models_to_responses` sends chat completion requests with tools to the Responses API when the datasheet marks the model as not supporting `reasoning_with_tool_calls`, and converts the answer back to chat format, so reasoning is kept instead of turned off. Defaults to `true`, also available per request through `x-bf-compat`
- **Chat reasoning.mode and reasoning.summary** - A chat request carrying `reasoning.mode` (`standard` or `pro`) on OpenAI or Azure is served through the Responses API so `pro` is honoured; other providers report it as a dropped compat param. Chat requests can also set `reasoning.summary` (`auto`, `concise`, `detailed`), forwarded when chat is served through the Responses API
- **DeepSeek Served Model Tracking** - When DeepSeek serves a different model than requested (retired IDs silently upgraded), the served model is recorded as `ServerSideFallbackModel` for pricing and routing info, and a datasheet `server_side_model` covers the Anthropic-compatible endpoint, which echoes the requested ID
- **Failure Classification and Smarter Key Rotation** - Every failed attempt now gets a `failure_class` on the attempt trail (`credential`, `quota`, `model_access`, `model_gone`, `region_blocked`, `rate_limit`, `transient`, `caller_fault`, `timeout`, `cancelled`, `unknown`), read from provider error codes rather than status alone. Credential and quota failures hold a key out for every model; keys refused for the model, a retired model or a region block are rotated past, and permanent per-key failures walk the key pool even at `max_retries: 0`. Attempts Bifrost ends itself are recorded as `timeout` (504) or `cancelled` (499). Provider retry hints (`Retry-After`, `retry-after-ms`, Gemini `RetryInfo`) are exposed as `extra_fields.retry_after_ms`, clamped to 1s to 5m
- **Time-to-First-Token Cutoff** - Routing rule targets accept `ttft_timeout_ms` (1 to 300000). A streaming attempt that does not produce its first token in time is cut off and handed to the next fallback without cancelling the request; the last attempt is never cut off, and non-streaming requests are unaffected. A cut-off attempt fails with code `ttft_timeout` and status `504` on the attempt trail. The rule editor has a "Time to first token cutoff (ms)" field per target, also in Helm
- **Requested Route in Routing Info** - When a routing rule, load balancer or session router rewrites the model or provider, the caller's original route is returned as `routing_info.requested_provider` / `requested_model` and in the `x-bifrost-routing-info-requested-provider` and `x-bifrost-routing-info-requested-model` response headers
- **Gateway Request ID Header** - Every traced response now carries `x-bifrost-request-id`, the ID the request is logged under (`GET /api/logs/{id}`), next to `x-bifrost-trace-id`. Provider response headers whose names start with `x-bifrost-` are no longer forwarded to the caller
- **Deprecated Models Hidden from Browsing** - `GET /api/models` without a `query` now leaves out deprecated models and their counts; with a `query` they are kept but sorted last. Pass `include_deprecated=true` to get them all
- **Provider Objects Bound to the Creating Virtual Key** - Files, batches, videos, containers (and container files) and cached contents created through a virtual key are now recorded in a new `provider_objects` table. Retrieve, content, delete, cancel, results and remix on another key's object return `404`, list pages are narrowed to the caller's own objects, and indirect references (a batch on another key's input file, a container with `file_ids`, a request naming `cached_content`) are checked the same way under every id form the provider accepts. A failed ownership lookup returns `500` instead of an unchecked page, and id lists over 1000 no longer fail large list pages. A new **Restrict Provider Objects to the Creating Virtual Key** switch under Settings > Security (`client.enforce_vk_object_ownership`, default `true`, applied without a restart) turns the restriction off; creators are still recorded while it is off
- **File-Based Batches Under Model-Restricted Virtual Keys** - A batch defined by `input_file_id` or `input_blob` is now judged by what the provider actually runs. On OpenAI and Azure (and custom providers built on them), which run the models named inside the file, the virtual key must allow every model of the provider. On Gemini, Vertex and Bedrock the request `model` must be present and allowed. A batch create that sends a file or blob together with inline `requests` returns `400`
- **Passthrough Route Hardening** - Passthrough routes (`/openai_passthrough`, `/anthropic_passthrough`, `/azure_passthrough`, `/genai_passthrough` and siblings) now forward only `POST` requests to a fixed allowlist of inference paths per provider (chat, completions, responses, embeddings, moderations, audio, images, `generateContent`, `countTokens`, `predict` and similar). Paths that could change the upstream host (not rooted, `//`, userinfo `@`, schemes, backslashes, `..`, control characters, percent-encoded forms included) are refused, the final URL must stay on the provider's host, and `x-model-provider` can only confirm the route's provider. The model is read strictly from the JSON body, and governance checks every model a body names, including each task of a Runware task array
- **Management API Refuses Unlisted Browser Origins** - While dashboard auth is disabled or unconfigured, and on deployments with `config_store.enabled: false`, browser requests to `/api/*` (and `/ws` and `/metrics` without a config store) from an origin that is not localhost, the gateway's own origin, or listed in `client.allowed_origins` (patterns such as `https://*.example.com` work, a bare `*` does not count) now return `403`. Requests without an `Origin` header (CLI, SDKs), whitelisted routes and inference routes are unchanged, and enabling dashboard auth lifts the auth-off check
- **Real Auth Required for Secret References and Private Targets** - Requests admitted only because dashboard auth is off now get `403` when they: use `env.`/`vault.` references in MCP client credential fields (headers, connection string, OAuth, token exchange, TLS) on `POST /api/mcp/client` or `PUT /api/mcp/client/{id}`; create, re-point or redeliver to a webhook endpoint with `allow_private_network`; set an outbound endpoint (`collector_url`, `metrics_endpoint`, `push_gateway_url`, `endpoint`, `url`, `base_url`) or any `env.`/`vault.` reference on a built-in plugin (OTEL, telemetry); set, change or remove a Vertex key's `vertex_key_config.auth_credentials` (the JSON names the hosts the Google client dials); or delete MCP tool logs via `DELETE /api/mcp-logs`. config.json provisioning is not affected (thanks [@xujiantop-crypto](https://github.com/xujiantop-crypto)!)
- **Auth Config Changes Need Proof of Control** - When an admin account exists but dashboard auth is switched off, re-enabling auth or replacing the admin username or password through `PUT /api/config` now requires `current_password` (the stored admin password) or a valid `setup_token` in the request. The Security page asks for the current password in that case
- **Request Decompression Limits** - Compressed request bodies may now expand to at most 100 times their compressed size (1 MiB floor, `client.max_request_body_size_mb` ceiling), and a process-wide in-flight budget of four times the body cap bounds buffered decompression. The budget is charged for bytes actually inflated, so ordinary concurrent gzip traffic is not refused
- **Access Profiles for Teams, Business Units and Customers** - *(enterprise)* A team, business unit or customer can hold an access profile instead of its own budgets and rate limit, and every virtual key under it is governed by that profile. Virtual keys can now be owned by a business unit (`business_unit_id`), and a business unit holds at most one budget. config.json accepts `access_profile` on `governance.teams`, `governance.customers` and `governance.business_units`, roles accept the new `business-unit-data` and `customer-data` data access scopes, and the dashboard hides a key's own limit editors when a profile governs it
- **Per-Virtual-Key Content Logging Control** - Virtual keys have a tri-state `disable_content_logging`: omitted or `null` inherits `client.disable_content_logging`, `true` keeps that key's request and response content out of the log store and strips it from OpenTelemetry export (MCP arguments included), `false` keeps content in the log store even when the client setting turns it off. The per-request `x-bf-disable-content-logging` header still wins. The virtual key editor has an Inherit / Off / On select, and the CLI has `--disable-content-logging`
- **Auto-Delete Expired Virtual Keys** - Virtual keys can set `delete_after_expire` (requires `expires_at`, `400` otherwise). A daily job deletes flagged keys once they expire and posts one notification with the counts. The expiry picker has a matching option
- **Global Proxy in config.json and for All Outbound Traffic** - The global outbound proxy can be declared as a top-level `proxy_config` in config.json (`enabled`, `url`, `username`, `password`, `no_proxy`, `timeout`, `skip_tls_verify`, `enable_for_scim`, `enable_for_inference`, `enable_for_api`) and in Helm. With `enable_for_api` on, MCP connections, MCP OAuth discovery, model catalog sync, OpenTelemetry export, webhooks, skill fetches and plugin downloads go through it, each keeping its own SSRF policy. With `enable_for_inference` on, providers without their own `proxy_config` now actually send inference through it (the flag was stored but never read before), and multi-entry `no_proxy` lists match on both fasthttp and net/http paths
- **Adaptive Routing Incidents and Attempt Metadata** - *(enterprise)* Adaptive Routing has an **Incidents** page in the sidebar. Load balancer decisions for each attempt are written to log metadata under the reserved `bifrost_alb_` prefix (caller headers cannot spoof them) and hidden from the log filter sidebar and metadata grid. Docs cover held keys, incidents and the `/api/adaptive-routing` endpoints
- **Governance Dashboard Updates** - *(enterprise UI)* New Org Chart page under Governance and an enterprise Home landing page; Business Units navigation checks its own `BusinessUnits` permission; new `BackgroundJobs` RBAC resource; Warp follows RBAC; create, edit, delete and rotate controls follow the viewer's permissions with a tooltip explaining why they are disabled; the customers list shows a server-side team count
- **SSO and SCIM Updates** - Every SSO provider's SCIM block accepts `attributeProjectMappings` (add users to existing projects when an IdP attribute matches a value or glob; memberships granted by a rule are revoked when it stops matching) and `bulkSyncInterval` (directory reconcile interval, default `24h`, from `1h` to `30d`), in config.json and Helm. The generic SSO provider accepts a login `displayName`, and a new identity sync guide aligns the IdP setup docs
- **Audit Logs: Omit IP Addresses** - *(enterprise)* New `audit_logs.omit_ip_addresses` (Helm `omitIpAddresses`, default `false`) stops recording client IPs in audit logs. New events store no `request_ip` or initiator host, older IPs are hidden from APIs, exports and archives (not deleted), and IP search and filters are disabled. HMAC signatures stay valid
- **Attribution Context Keys Deprecated** - The raw attribution context keys (`BifrostContextKeyGovernanceVirtualKeyID`, `...TeamID`, `...CustomerID`, `...BusinessUnitID`, `...ProjectID`, `...BudgetIDs`, `...RateLimitIDs`, `BifrostContextKeyUserID`, `...UserName`, `...UserEmail` and related variants) are deprecated in favour of the `ctx.Grant()` accessors. Values and behavior are unchanged
- **MCP Client Target Validation at Connect Time** - MCP clients registered while dashboard auth is off now carry a server-set `require_public_target` flag, and every later dial (reconnects, per-call connections, proxied hops) is held to public addresses, not only the registration-time DNS check. Existing clients default to `false`
- **MCP OAuth Server Hardening** - Bifrost's MCP OAuth authorization server accepts remote client callback URIs only when listed in `client.oauth2_server_config.allowed_redirect_uris` (loopback and `cursor://anysphere.cursor-mcp` are always allowed), re-checks existing registrations at authorization and token exchange, and shows the exact callback on the consent page. Oversize DCR/authorize fields (`client_name`, `scope`, `redirect_uris`, `state`, `code_challenge`) return `400` before anything is stored
- **MCP OAuth Private Network Allowlist** - OAuth-protected MCP servers on localhost or a private network can now be added. List hostnames, IPs or CIDRs in `client.mcp_oauth_private_allowlist` (or `mcp.tool_manager_config.oauth_private_allowlist`, which wins) and the MCP OAuth chain (discovery, dynamic client registration, token exchange, refresh) may reach them for clients registered by an authenticated admin or declared in config.json. Link-local and cloud metadata addresses stay blocked, invalid entries stop boot, and edits apply to the next connection
- **Virtual Key Rotation Revokes MCP OAuth Grants** - Rotating a virtual key now revokes the MCP OAuth refresh tokens minted with its old value and any consented but unexchanged authorization code, in the same transaction as the rotation. OAuth consent in vk mode requires the key's current value
- **MCP Server Instructions** - The `instructions` an upstream MCP server returns from its `initialize` handshake are now captured, persisted with discovered tools and refreshed with them. Bifrost forwards them on its own `/mcp` gateway and injects them into MCP-bearing chat (as a leading system message) and Responses (appended to `instructions`) requests as tagged `<mcp_server name="...">` blocks, scoped to the servers the request can see. Caps are `mcp.tool_manager_config.max_instructions_per_client` (default 4096 bytes), `max_instructions_total` (default 16384 bytes) and a per-client `max_instructions_length` override. In code mode the instructions appear in the `.pyi` stubs
- **MCP Connection Recovery and Tool Refresh** - `POST /api/mcp/client/{id}/refresh-tools` (and a **Refresh tools** action in the client table) re-discovers a client's tools immediately, for every client type including per-user and per-call clients. Tool calls that fail because the server dropped its session ("session terminated", "session not found", "need to re-initialize") trigger an immediate reconnect and, where safe, a retry; a failed live-connection check now triggers the documented reconnect, and a failed make-before-break re-dial keeps the live connection. Health probes retry timeouts but treat dead sessions and auth rejections as permanent. `POST /api/mcp/client/{id}/reregister` (dashboard: "Reauthorize with a new client") registers a new dynamic OAuth client and runs consent against it when the upstream forgot the old `client_id`
- **Code Mode Execution Limits** - Code mode now runs in-process on a pinned Starlark runtime with per-execution budgets instead of child processes. ## 🗄️ Database Migrations

This release adds 45 config store and 9 log store migrations. Most add nullable or defaulted columns, new tables, or indexes, and are safe to run while older pods are still serving. The items with a Note need attention before or during the upgrade.

The migration runner now reads the list of applied IDs once at startup and skips steps that are already recorded, so restarts no longer re-run finished steps (#7994). Postgres index checks are scoped to the current schema, and an INVALID index left behind by an interrupted build is dropped and rebuilt (#8439).

### Config store: data moves and backfills

- **move_config_json_vk_limits_to_model_configs** - Moves budgets and rate limits that a virtual key or a virtual key provider config owned directly onto all-models model configs, creating those configs when needed. Non-reversible: the original owner is not recorded. What changes: while the rollout runs, pods still on 2.2.6 no longer see these limits on the virtual key or provider config, so they stop enforcing them until they are replaced. What to do: upgrade all pods in one short window, or scale down to one pod for the upgrade, if enforcing those limits during the rollout matters.
- **backfill_compat_force_reasoning_only_models_to_responses** - Sets `compat_force_reasoning_only_models_to_responses` to `true` on every existing client config row. Non-reversible: the rollback does nothing. What changes: chat requests with tools to models that cannot reason with tool calls are routed to the Responses API on existing deployments after the upgrade. What to do: to keep the 2.2.6 behaviour, set `client.compat.force_reasoning_only_models_to_responses: false` in config.json (UI: Settings, Compatibility) after upgrading.
- **move_pricing_override_search_context_to_web_search** - Renames the `search_context_cost_per_query` key to `web_search_cost_per_request` inside saved pricing overrides. Non-reversible: no rollback. What changes: pods still on 2.2.6 do not see the old key in overrides during the rollout. What to do: rename `search_context_cost_per_query` to `web_search_cost_per_request` in any pricing override you keep in config.json.
- **add_web_search_cost_per_request_column** - Adds `model_pricing.web_search_cost_per_request` and copies existing `search_context_cost_per_query` rates into it. Reversible: drops the column.
- **add_batch_jobs_due_index** - Clears `next_check_at` on settled and unpriceable batch jobs (in batches of 10,000), then builds the partial index `idx_batch_jobs_due` concurrently. Non-reversible: cleared values cannot be restored.
- **add_client_config_enforce_vk_object_ownership_column** - Adds `config_client.enforce_vk_object_ownership` with default `true` and sets existing rows to `true`. Reversible: drops the column. What changes: files, batches, containers and cached content created through a virtual key can only be read, listed or deleted through that same virtual key. What to do: set `client.enforce_vk_object_ownership: false` in config.json (UI toggle under virtual key settings) if clients share provider objects across virtual keys.

### Config store: unique indexes on existing data

### Log store

- **logs_add_owner_timestamp_indexes**, **logs_add_ranking_name_timestamp_indexes** - Replace the single-column `virtual_key_id`, `user_id`, `team_id`, `selected_key_id`, `routing_rule_id`, `customer_id`, `business_unit_id` and `project_id` indexes on `logs` (and the owner indexes on `mcp_tool_logs`) with `(column, timestamp)` composites. On Postgres the rollback does not restore the old indexes. What changes: a 2.2.6 pod that restarts during the rollout, or after a rollback, rebuilds the old single-column indexes in the background on a large `logs` table, and 2.3.0 pods then drop them again. What to do: on large Postgres log stores, finish the rollout without restarting old pods, and expect extra index build I/O right after the upgrade.
- **agent_logs_init** - Adds `logs.agent_correlation_id`, `mcp_tool_logs.session_id` and `mcp_tool_logs.agent_correlation_id`, and creates `agent_logs`. It takes brief locks on `logs` and `mcp_tool_logs`, bounded by a 5s lock timeout. Its indexes are built in the background, concurrently on Postgres. Reversible only while the new table and columns are empty.
- **agent_logs_add_raw_payload_columns** - Adds `agent_logs.raw_request` and `raw_response`. Non-reversible: the rollback would delete recorded transport bodies.
- **logs_add_warp_conversation_tables** - Creates `warp_conversations` and `warp_messages`. Reversible only while they are empty.
- **logs_add_warp_message_outcome_columns** - Adds `finish_reason`, `total_tokens`, `cost` and `question_json` to `warp_messages`. Reversible only while no outcome is recorded.
- **logs_add_warp_conversations_updated_at_index** - Concurrent index on `warp_conversations(updated_at DESC)`. Reversible.
- **logs_add_embedding_input_column** - Adds `logs.embedding_input`. Reversible.
- **logs_add_live_session_column** - Adds `logs.live_session`. Reversible.
- **Background jobs** - The invalid-metadata cleanup and the `cached_read_tokens` backfill now walk `logs` in one-hour windows and run once. Completion is recorded in the migrations table as `logs_bg_invalid_metadata_cleanup_v1` and `logs_bg_cached_read_tokens_backfill_v1`.
