# One-click deployments

Everything behind the "Deploy to the cloud in one click" buttons in the docs and README.

| Button | Mechanism | Lives in |
|---|---|---|
| Deploy on Railway | Railway template published from the Maxim workspace (Bifrost service + Postgres) | Railway dashboard; runbook in [railway/README.md](railway/README.md) |
| Deploy to Render | Render Blueprint: web service from the published image + Render Postgres | [`render.yaml`](../render.yaml) at the repository root |
| Deploy on AWS | AWS CloudShell + Terraform: ECS Fargate, RDS PostgreSQL 16, ALB | [`aws/deploy.sh`](aws/deploy.sh) over [`terraform/examples/aws-ecs-postgres`](../terraform/examples/aws-ecs-postgres) |
| Deploy on GCP | Google Cloud Shell + Terraform: Cloud Run, Cloud SQL PostgreSQL 16 | [`gcp/deploy.sh`](gcp/deploy.sh) over [`terraform/examples/gcp-cloud-run-postgres`](../terraform/examples/gcp-cloud-run-postgres) |
| Deploy on Azure | Azure Cloud Shell + Terraform: Container Instances, PostgreSQL Flexible Server 16. Plain HTTP endpoint: add TLS (Front Door or Application Gateway) before creating the admin account, see the guide | [`azure/deploy.sh`](azure/deploy.sh) over [`terraform/examples/azure-aci-postgres`](../terraform/examples/azure-aci-postgres) |
| Deploy on Fly.io | flyctl from your terminal: one Machine + Fly Postgres attached as `DATABASE_URL` | [`fly/deploy.sh`](fly/deploy.sh) with [`fly/fly.toml`](fly/fly.toml) |

All six produce the same shape of deployment: one Bifrost instance, PostgreSQL 16 for the config store and the log store, a generated encryption key, a generated setup token for the first admin account, and `enforce_auth_on_inference` on so a public endpoint needs a virtual key.

## Shared configuration

[`config.postgres.json`](config.postgres.json) is the `config.json` every path ships. Each value is an `env.` reference, so the document is identical everywhere and only the environment differs:

| Variable | Railway / Render | Fly.io | AWS | GCP | Azure |
|---|---|---|---|---|---|
| `PG_HOST` | platform database host | derived from `DATABASE_URL` | RDS address | `/cloudsql/<connection name>` (unix socket) | Flexible Server FQDN |
| `PG_PORT` | platform database port | derived from `DATABASE_URL` | RDS port | `5432` | `5432` |
| `PG_USER`, `PG_PASSWORD`, `PG_DATABASE` | platform database | derived from `DATABASE_URL` | Secrets Manager + Terraform | Secret Manager + Terraform | secure env + Terraform |
| `PG_SSL_MODE` | Railway `require` (its Postgres serves TLS; `prefer` would allow a plaintext fallback), Render `prefer` (the Blueprint value) | from `?sslmode=` (Fly Postgres: `disable`) | `require` | `disable` (the connector encrypts) | `require` |
| `BIFROST_ENCRYPTION_KEY`, `BIFROST_SETUP_TOKEN` | generated by the platform | generated by the script as Fly secrets | Secrets Manager | Secret Manager | secure env variables |

Railway, Render and Fly.io hand the document to the container through `BIFROST_CONFIG_JSON`; the image entrypoint writes it to `/app/data/config.json` on first boot and never overwrites an existing file. When a platform attaches Postgres as a single `DATABASE_URL`, the entrypoint derives any `PG_*` value that is not already set from it. The Terraform paths keep storing `config.json` in the cloud secret manager (Key Vault on Azure) as before.

## Enterprise

Bifrost Enterprise ships from a private registry path issued per organization, so there is no public enterprise button. Every path takes the image as one setting:

- Render: edit `image.url` in `render.yaml` and add `image.creds.fromRegistryCreds` (the service-level `registryCredential` field is for Dockerfile builds, not `runtime: image`).
- Railway: change the service image and registry credentials in the service settings after deploying the template.
- AWS, GCP and Azure: set `BIFROST_IMAGE_REPOSITORY` before running the deploy script (or `image_repository` in `terraform.tfvars`; the scripts keep an existing `terraform.tfvars`, so edits survive reruns). Azure Container Instances also need the pull credential: `registry_server`, `registry_username` and `registry_password` in `terraform.tfvars`, which become an `image_registry_credential` on the container group. AWS and GCP use the execution role or service account permissions the enterprise guides describe.
- Fly.io: Fly pulls private images only from its own registry, and `registry.fly.io/<app>` exists only once the app does. Create it first (`fly apps create <app> --org <org>`), pull and retag the image, `fly auth docker`, push it to `registry.fly.io/<app>:<tag>`, then run the deploy script with `FLY_APP_NAME=<app>`, `FLY_ORG=<org>` unless the app is in your personal organization (the script looks for the app only in that organization and reuses it there; without `FLY_ORG` it would try to create a second one), and `BIFROST_IMAGE` set to that reference.

Enterprise requires PostgreSQL for both stores, which is exactly what every path provisions.

## Versioning

`render.yaml` pins the image tag; `.github/workflows/scripts/bump-deploy-image-tags.sh` moves it on each stable transport release. The Terraform examples, the Fly.io config and the Railway template default to `latest` so a fresh clone or template deploy always works, and the docs tell operators to pin afterwards.
