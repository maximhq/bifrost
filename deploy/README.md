# One-click deployments

Everything behind the "Deploy to the cloud in one click" buttons in the docs and README.

| Button | Mechanism | Lives in |
|---|---|---|
| Deploy on Railway | Railway template published from the Maxim workspace (Bifrost service + Postgres) | Railway dashboard; runbook in [railway/README.md](railway/README.md) |
| Deploy to Render | Render Blueprint: web service from the published image + Render Postgres | [`render.yaml`](../render.yaml) at the repository root |
| Deploy on DigitalOcean | App Platform template: web service from the published image + dev PostgreSQL bound as `DATABASE_URL` | [`.do/deploy.template.yaml`](../.do/deploy.template.yaml) |
| Deploy to Koyeb | Button URL carrying image, port and variables; database created first by the user | [`koyeb/README.md`](koyeb/README.md) |
| Deploy to Heroku | `app.json` + `heroku.yml` on the container stack with Heroku Postgres; the build is a one-line `FROM` of the published image | [`app.json`](../app.json), [`heroku.yml`](../heroku.yml), [`heroku/Dockerfile`](heroku/Dockerfile) |
| Deploy on AWS | AWS CloudShell + Terraform: ECS Fargate, RDS PostgreSQL 16, ALB | [`aws/deploy.sh`](aws/deploy.sh) over [`terraform/examples/aws-ecs-postgres`](../terraform/examples/aws-ecs-postgres) |
| Deploy on GCP | Google Cloud Shell + Terraform: Cloud Run, Cloud SQL PostgreSQL 16 | [`gcp/deploy.sh`](gcp/deploy.sh) over [`terraform/examples/gcp-cloud-run-postgres`](../terraform/examples/gcp-cloud-run-postgres) |
| Deploy on Azure | Azure Cloud Shell + Terraform: Container Instances, PostgreSQL Flexible Server 16. Plain HTTP endpoint: add TLS (Front Door or Application Gateway) before creating the admin account, see the guide | [`azure/deploy.sh`](azure/deploy.sh) over [`terraform/examples/azure-aci-postgres`](../terraform/examples/azure-aci-postgres) |
| Deploy on Fly.io | flyctl from your terminal: one Machine + Fly Postgres attached as `DATABASE_URL` | [`fly/deploy.sh`](fly/deploy.sh) with [`fly/fly.toml`](fly/fly.toml) |

All nine produce the same shape of deployment: one Bifrost instance, PostgreSQL for the config store and the log store, an encryption key, a setup token for the first admin account, and `enforce_auth_on_inference` on so a public endpoint needs a virtual key. Two details differ by platform. The Terraform paths, Render, Railway and Fly.io generate the two secrets; DigitalOcean and Koyeb cannot, so their templates carry placeholders that you replace with your own values on the review form before the first deploy (a placeholder left in place is a publicly known setup token). The Terraform paths provision PostgreSQL 16, Render pins 16 in the Blueprint, Railway and Fly.io use the platform's current Postgres image, Heroku's add-on uses Heroku's current default major, DigitalOcean's dev database is version 16, and Koyeb uses whatever database you attach (16 or later).

## Shared configuration

[`config.postgres.json`](config.postgres.json) is the `config.json` every path ships. Each value is an `env.` reference, so the document is identical everywhere and only the environment differs:

| Variable | Railway / Render | Fly.io, DigitalOcean, Koyeb, Heroku | AWS | GCP | Azure |
|---|---|---|---|---|---|
| `PG_HOST` | platform database host | derived from `DATABASE_URL` | RDS address | `/cloudsql/<connection name>` (unix socket) | Flexible Server FQDN |
| `PG_PORT` | platform database port | derived from `DATABASE_URL` | RDS port | `5432` | `5432` |
| `PG_USER`, `PG_PASSWORD`, `PG_DATABASE` | platform database | derived from `DATABASE_URL` | Secrets Manager + Terraform | Secret Manager + Terraform | secure env + Terraform |
| `PG_SSL_MODE` | Railway `require` (its Postgres serves TLS; `prefer` would allow a plaintext fallback), Render `prefer` (the Blueprint value) | from `?sslmode=`, else `prefer` | `require` | `disable` (the connector encrypts) | `require` |
| `BIFROST_ENCRYPTION_KEY`, `BIFROST_SETUP_TOKEN` | generated by the platform | Fly: script; Heroku: `generator: secret`; DigitalOcean and Koyeb: entered on the review form | Secrets Manager | Secret Manager | secure env variables |

Railway, Render, Fly.io, DigitalOcean, Koyeb and Heroku hand the document to the container through `BIFROST_CONFIG_JSON` (Koyeb: `BIFROST_CONFIG_B64`, because the value travels in a URL); the image entrypoint writes it to `/app/data/config.json` on first boot and never overwrites an existing file. When a platform attaches Postgres as a single `DATABASE_URL`, the entrypoint derives any `PG_*` value that is not already set from it. The Terraform paths keep storing `config.json` in the cloud secret manager (Key Vault on Azure) as before.

## Enterprise

Bifrost Enterprise ships from a private registry path issued per organization, so there is no public enterprise button. Every path takes the image as one setting:

- Render: edit `image.url` in `render.yaml` and add `image.creds.fromRegistryCreds` (the service-level `registryCredential` field is for Dockerfile builds, not `runtime: image`).
- Railway: change the service image and registry credentials in the service settings after deploying the template.
- AWS, GCP and Azure: set `BIFROST_IMAGE_REPOSITORY` before running the deploy script (or `image_repository` in `terraform.tfvars`; the scripts keep an existing `terraform.tfvars`, so edits survive reruns). Azure Container Instances also need the pull credential: `registry_server`, `registry_username` and `registry_password` in `terraform.tfvars`, which become an `image_registry_credential` on the container group. AWS and GCP use the execution role or service account permissions the enterprise guides describe.
- Fly.io: Fly pulls private images only from its own registry, and `registry.fly.io/<app>` exists only once the app does. Create it first (`fly apps create <app> --org <org>`), pull and retag the image, `fly auth docker`, push it to `registry.fly.io/<app>:<tag>`, then run the deploy script with `FLY_APP_NAME=<app>`, `FLY_ORG=<org>` unless the app is in your personal organization (the script looks for the app only in that organization and reuses it there; without `FLY_ORG` it would try to create a second one), and `BIFROST_IMAGE` set to that reference.
- DigitalOcean: the button template wraps the app spec in a top-level `spec:` key, so first extract that inner document into an owner-only file outside the clone (`(umask 077 && yq '.spec' .do/deploy.template.yaml > ~/bifrost-app.yaml)`; delete it after the deploy, since it will hold the credential and the secrets), App Platform pulls only from DigitalOcean Container Registry, Docker Hub and GitHub Container Registry, not from the Artifact Registry path the enterprise guide issues, so first mirror the Enterprise image into one of those (DOCR is the simplest), then set the image fields there: for DOCR, `registry_type: DOCR`, an empty `registry` (App Platform requires it empty for DOCR; the template carries `maximhq`), `repository` and `tag` (the mirrored tag; the template pins the OSS release); for Docker Hub or GHCR, `registry` is the organization and `registry_credentials` is `username:token`. App Platform runs `linux/amd64` images only, so mirror that architecture. replace the two `REPLACE_WITH_` secret placeholders (`BIFROST_ENCRYPTION_KEY`, `BIFROST_SETUP_TOKEN`) with your own random values (the public template's values are known to everyone, and the setup token creates the first admin account), and create the app with `doctl apps create --spec ~/bifrost-app.yaml`; or create the app in the control panel and attach the registry credential there. Never add `registry_credentials` to the public repository the button reads: App Platform only encrypts the value once it has been submitted, and the button requires that repository to be public.
- Koyeb: on the review form, change the image to the registry path issued for your organization and add the registry secret (the form has a registry credential field) before the first deploy; the credential alone leaves the public image selected, and a deploy without it cannot pull the private image.
- Heroku: Heroku cannot build from a private `FROM` line. Pull the Enterprise image with its credential for `linux/amd64` (`docker pull --platform linux/amd64 <image>`; Heroku runs x86-64 images only, and a multi-architecture pull on an ARM workstation would otherwise resolve to ARM64), tag it `registry.heroku.com/<app>/web`, run `heroku container:login`, push it, then `heroku container:release web --app <app>`.

Enterprise requires PostgreSQL for both stores, which is exactly what every path provisions.

## Versioning

`render.yaml`, `.do/deploy.template.yaml` and `deploy/heroku/Dockerfile` pin the image tag; `.github/workflows/scripts/bump-deploy-image-tags.sh` moves them on each stable transport release. The Terraform examples, the Fly.io config, the Koyeb button and the Railway template default to `latest` so a fresh clone or template deploy always works, and the docs tell operators to pin afterwards.
